5절에서 배운 건 망한 뒤에 되돌리는 법이고, 이 절은 애초에 본줄기가 안 망하게 하는 법입니다. 여기서 만든 가지가 [[07-배포PR/_스테이지|Stage 7]]에서 그대로 PR이 됩니다 — THE CHAIN이 여기를 지납니다.

## ① 가지가 무엇인지 그림으로 본다

`main`이라는 본줄기가 하나 있고, 지금까지 커밋한 게 전부 여기 쌓였습니다. 가지를 만든다는 건 그 지점에서 옆으로 길을 하나 내는 것입니다.

```
main:   ●───●───●───────────●   ← 본줄기는 그대로
                 \         /
가지:              ●───●─┘      ← 옆에서 따로 해 보고, 됐으면 합침
```

옆 길에서 무슨 짓을 해도 본줄기는 멀쩡합니다. 잘되면 합치고(merge), 안 되면 가지를 버립니다. **버리는 게 공짜라는 게 핵심입니다.** 「이 기능 전체를 다시 짜줘」를 가지에서 시키면, 결과가 엉망이어도 가지를 지우면 아무 일도 없던 게 됩니다.

## ② 1인 방식을 정한다

인터넷의 브랜치 전략은 전부 여러 명을 전제로 만든 것입니다. 릴리스 담당·리뷰어·배포 승인자 사이의 경계를 그으려는 규칙인데, 혼자면 그 경계가 전부 나 하나입니다.

> **`main` 하나 + 작업마다 짧은 가지 하나**

| 항목 | 규칙 |
|---|---|
| 본줄기 | `main` 하나. 항상 돌아가는 상태를 유지합니다 |
| 가지 이름 | 무슨 일인지 알아볼 수 있게. `login-fix`, `payment-ui` |
| 가지 수명 | 짧게. 하루이틀, 길어도 며칠 |
| 합친 뒤 | 지웁니다. 안 지우면 목록이 쓰레기통이 됩니다 |

가지를 오래 두면 그동안 `main`도 앞으로 갑니다. 둘이 벌어질수록 합칠 때 충돌이 늘어나니, 작게 나눠서 자주 합치는 게 덜 아픕니다.

## ③ 한 바퀴를 돈다

만들고, 일하고, 합치고, 지웁니다.

```bash
git switch -c login-fix
```
> `login-fix`라는 가지를 만들고 그리로 이동합니다. `-c`가 「만들면서」라는 뜻입니다.

```bash
git branch
```
> 가지 목록을 보여 줍니다. 지금 있는 가지 앞에 `*`가 붙습니다.

여기서 평소대로 파일을 고치고 `git add`·`git commit`합니다. 이 커밋들은 `main`에 안 보이고 옆 길에만 쌓입니다.

```bash
git push -u origin login-fix
```
> 이 가지를 GitHub에도 올립니다. 처음 한 번만 `-u origin 가지이름`을 붙이고, 다음부터는 `git push`만 하면 됩니다.

```bash
git switch main
```
> 본줄기로 돌아옵니다. 파일 내용이 통째로 바뀌어 가지에서 만든 게 안 보이는 게 정상입니다.

```bash
git merge login-fix
```
> 가지에서 한 일을 본줄기에 합칩니다. 그 뒤 `git push`로 올립니다.

```bash
git branch -d login-fix
git push origin --delete login-fix
```
> 내 컴퓨터와 GitHub 양쪽에서 가지를 지웁니다. `-d`는 합쳐진 것만 지워서 안전합니다.

합치지 않고 버릴 때는 `git switch main` 뒤에 `git branch -D login-fix`를 칩니다. **대문자 `-D`는 안 합쳐졌어도 지웁니다.** 본줄기는 아무 영향 없습니다.

## ④ 충돌을 푼다

합칠 때 같은 줄을 양쪽에서 다르게 고쳤으면 Git이 판단을 미룹니다. 이런 게 파일에 들어옵니다.

```
<<<<<<< HEAD
본줄기 쪽 내용
=======
가지 쪽 내용
>>>>>>> login-fix
```

**에러가 아닙니다.** 「둘 중 뭘 남길지 네가 정해라」는 뜻이라, 표시 줄까지 다 지우고 남길 내용만 남기면 됩니다. 혼자 작업하면 드물고, 나더라도 AI에게 맡기되 결정은 내가 합니다.

```
merge 하다가 충돌이 났어. 충돌 난 파일을 열어서 양쪽이 각각 무슨 의도였는지 설명해주고,
어느 쪽을 남기는 게 맞는지 추천해줘. 내가 고르면 그때 정리해줘.
```

## ⚡ 따라 하기

진짜 저장소에서 한 바퀴를 끝까지 도세요. 사소한 변경 하나로 충분합니다.

1. 가지를 만들고 어디 있는지 확인하세요. 본줄기를 안 건드리는 첫걸음입니다. `* 연습가지`에 별표가 붙어 있어야 합니다.

```bash
git switch -c 연습가지
git branch
```
> 가지를 만들고 → 목록을 봅니다.

2. 한 줄 고치고 커밋해서 GitHub에 올리세요. 가지도 인터넷 창고에 올라간다는 걸 보기 위해서입니다. GitHub 웹페이지 가지 목록에 「연습가지」가 보여야 합니다.

```bash
echo "가지에서 쓴 줄" >> README.md
git add README.md && git commit -m "README에 한 줄 추가"
git push -u origin 연습가지
```
> 고치고 → 커밋하고 → 올립니다.

3. 화면에 **Compare & pull request** 버튼이 떠 있어도 지금은 누르지 마세요. [[07-배포PR/_스테이지|Stage 7]]에서 그 버튼을 씁니다.

4. 본줄기로 돌아와 합치고 올리세요. `main`에 그 한 줄이 들어와야 합니다.

```bash
git switch main
git merge 연습가지
git push
```
> 본줄기로 돌아와 → 합치고 → 올립니다.

5. 다 쓴 가지를 양쪽에서 지우세요. GitHub 가지 목록에서 「연습가지」가 사라져야 합니다.

```bash
git branch -d 연습가지
git push origin --delete 연습가지
```
> 내 컴퓨터와 GitHub에서 가지를 지웁니다.

6. 가지 쓰는 습관을 AI에게 박아 두세요. 큰 변경 전에 `main`에 있으면 AI가 먼저 말해 주게 됩니다.

```
이 프로젝트의 CLAUDE.md 에 브랜치 규칙을 적어줘. 내용은 이 셋:

1. main에서 직접 작업하지 않는다. 작업마다 짧은 브랜치를 하나 만든다
2. 브랜치 이름은 무슨 일인지 알아볼 수 있게 영어 소문자와 하이픈으로 짓는다
3. 큰 변경을 시작하기 전에는 반드시 지금 어느 브랜치인지 확인하고,
   main이면 브랜치를 먼저 만들자고 나에게 말한다
```

## ✅ 확인

- [ ] `git branch`를 쳤을 때 지금 어느 가지에 있는지 별표로 보이나
- [ ] 가지에서 커밋하고 `main`으로 돌아갔을 때 그 변경이 안 보였나 (안 보여야 정상)
- [ ] 합친 뒤 `main`에서 그 변경이 보이나
- [ ] GitHub 웹페이지의 가지 목록에서 연습 가지가 지워졌나

## 📘 말 풀이

**브랜치(branch, 가지)** — 본줄기를 건드리지 않고 옆에서 따로 해 보는 길. 만드는 것도 지우는 것도 순식간이고 지워도 본줄기에 흔적이 없습니다. `main`은 관례적으로 붙는 본줄기의 이름입니다.

**병합(merge, 합치기)** — 가지에서 한 일을 본줄기로 가져오는 것. 합치고 나면 가지의 커밋들이 본줄기 기록에도 들어옵니다.

**충돌(conflict)** — 같은 파일의 같은 줄을 양쪽에서 다르게 고쳐서 Git이 못 정하는 상태. 고장이 아니라 사람에게 넘긴 질문입니다.

## ⚠️ 함정

**가지에서 일하는 걸 잊고 `main`에서 그냥 작업합니다.** 가장 흔합니다. 작업 시작 전에 `git branch`로 지금 어디인지 확인하는 걸 습관으로 만드세요.

**가지를 만들기 전에 커밋을 안 합니다.** 안 커밋한 변경은 가지를 옮겨도 따라와서 헷갈립니다. 옮기기 전에 커밋하거나 `git stash`로 치워 둡니다.

**`git switch main`을 했는데 파일이 사라졌다고 놀랍니다.** 사라진 게 아니라 가지에 그대로 있습니다. 다시 `git switch 가지이름`을 치면 돌아옵니다.

**복잡한 브랜치 전략을 따라 하려 합니다.** 개발 가지·릴리스 가지·핫픽스 가지를 혼자 운영하면 일보다 규칙 지키기에 시간이 더 듭니다. 협업자가 생기면 그때 늘립니다.
