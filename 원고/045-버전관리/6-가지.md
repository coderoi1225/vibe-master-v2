## 왜 이걸 하나

5절에서 배운 건 **망한 뒤에 되돌리는 법**입니다.
이 절은 **애초에 본줄기가 안 망하게 하는 법**입니다.

가지를 쓰면 이렇게 됩니다.

> 새 기능을 시도합니다 → 마음에 안 듭니다 → **가지를 지웁니다** → 끝.
> 되돌릴 것도 없습니다. **본줄기는 처음부터 안 건드렸으니까요.**

그리고 하나 더 — **여기서 만든 가지가 [[07-배포PR/_스테이지|Stage 7]]에서 그대로 PR이 됩니다.**
가지 없이는 PR이 없고, PR이 없으면 자동 검사를 걸 문이 없습니다. **THE CHAIN이 여기를 지납니다.**

## 가지가 뭔가

`main`이라는 **본줄기**가 하나 있습니다. 지금까지 커밋한 게 전부 여기 쌓였습니다.

가지를 만든다는 건 **그 지점에서 옆으로 길을 하나 내는 것**입니다.

```
main:   ●───●───●───────────●   ← 본줄기는 그대로
                 \         /
가지:              ●───●─┘      ← 옆에서 따로 해 보고, 됐으면 합침
```

옆 길에서 무슨 짓을 해도 **본줄기는 멀쩡합니다.**
잘되면 합치고(merge), 안 되면 가지를 버립니다. **버리는 게 공짜라는 게 핵심입니다.**

**AI에게 큰 걸 시킬 때 특히 그렇습니다.** 「이 기능 전체를 다시 짜줘」를 가지에서 시키면,
결과가 엉망이어도 **가지를 지우면 아무 일도 없던 게 됩니다.**

## 1인에게 맞는 방식 — 딱 이것만

인터넷에서 브랜치 전략을 찾아보면 이름 붙은 방식이 여럿 나옵니다. **전부 여러 명을 전제로 만든 것입니다.**
릴리스 담당, 리뷰어, 배포 승인자가 따로 있는 조직에서 **역할 사이의 경계**를 그으려고 만든 규칙입니다.
혼자면 그 경계가 전부 나 하나입니다. 규칙만 남고 이유가 없어집니다.

**혼자는 이거면 충분합니다.**

> ## `main` 하나 + 작업마다 짧은 가지 하나

| 항목 | 규칙 |
|---|---|
| 본줄기 | **`main` 하나.** 항상 돌아가는 상태를 유지합니다 |
| 가지 이름 | 무슨 일인지 알아볼 수 있게. `login-fix`, `payment-ui` |
| 가지 수명 | **짧게.** 하루이틀, 길어도 며칠. 오래 두면 합칠 때 아픕니다 |
| 합친 뒤 | **지웁니다.** 안 지우면 목록이 쓰레기통이 됩니다 |

**「짧게」가 왜 중요한가** — 가지를 오래 두면 그동안 `main`도 앞으로 갑니다. 둘이 벌어질수록 합칠 때 충돌이 늘어납니다. **작게 나눠서 자주 합치는 게 덜 아픕니다.**

## 한 바퀴 — 만들고, 일하고, 합치고, 지운다

### ① 가지를 만들고 그리로 옮겨 갑니다

```bash
git switch -c login-fix
```
> `login-fix`라는 가지를 만들고 그리로 이동합니다. (`-c`가 「만들면서」라는 뜻입니다)

```bash
git branch
```
> 가지 목록을 보여 줍니다. 지금 있는 가지 앞에 `*`가 붙습니다.

### ② 거기서 일하고 커밋합니다

평소대로 합니다. 파일을 고치고, `git add`하고, `git commit`합니다.
**이 커밋들은 `main`에 안 보입니다.** 옆 길에만 쌓입니다.

```bash
git push -u origin login-fix
```
> 이 가지를 GitHub에도 올립니다. 처음 한 번만 `-u origin 가지이름`을 붙이고, 다음부터는 `git push`만 하면 됩니다.

### ③ 본줄기로 돌아와 합칩니다

```bash
git switch main
```
> 본줄기로 돌아옵니다. **파일 내용이 통째로 바뀝니다.** 가지에서 만든 게 안 보이는 게 정상입니다.

```bash
git merge login-fix
```
> 가지에서 한 일을 본줄기에 합칩니다.

```bash
git push
```
> 합친 결과를 GitHub에 올립니다.

### ④ 다 쓴 가지를 지웁니다

```bash
git branch -d login-fix
```
> 내 컴퓨터에서 그 가지를 지웁니다. (`-d`는 「합쳐진 것만 지운다」라 안전합니다. 안 합쳐졌으면 거부합니다)

```bash
git push origin --delete login-fix
```
> GitHub에서도 그 가지를 지웁니다.

**합치지 않고 버릴 때**

```bash
git switch main
git branch -D login-fix
```
> 본줄기로 돌아가서 → 가지를 **강제로** 지웁니다. (`-D` 대문자는 「안 합쳐졌어도 지운다」입니다) 시도해 봤는데 아니었을 때 이렇게 버립니다. **본줄기는 아무 영향 없습니다.**

## 충돌이 났을 때

합칠 때 **같은 줄을 양쪽에서 다르게 고쳤으면** Git이 판단을 미룹니다. 이런 게 파일에 들어옵니다.

```
<<<<<<< HEAD
본줄기 쪽 내용
=======
가지 쪽 내용
>>>>>>> login-fix
```

**에러가 아닙니다.** 「둘 중 뭘 남길지 네가 정해라」는 뜻입니다.
`<<<<<<<`, `=======`, `>>>>>>>` 줄까지 다 지우고 남길 내용만 남기면 됩니다.

혼자 작업하면 충돌은 드뭅니다. 나더라도 AI에게 맡기면 됩니다.

```
merge 하다가 충돌이 났어. 충돌 난 파일을 열어서 양쪽이 각각 무슨 의도였는지 설명해주고,
어느 쪽을 남기는 게 맞는지 추천해줘. 내가 고르면 그때 정리해줘.
```

**「내가 고르면」이 중요합니다.** 충돌은 판단이 필요한 자리라 AI에게 결정까지 맡기지 않습니다.

## 📘 말 풀이

**브랜치(branch, 가지)**
본줄기를 건드리지 않고 옆에서 따로 해 보는 길. 만드는 것도 지우는 것도 순식간이고, 지워도 본줄기에 아무 흔적이 없습니다. **`main`**은 관례적으로 붙는 본줄기의 이름입니다.

**병합(merge, 합치기)**
가지에서 한 일을 본줄기로 가져오는 것. 합치고 나면 가지의 커밋들이 본줄기 기록에도 들어옵니다.

**충돌(conflict)**
같은 파일의 같은 줄을 양쪽에서 다르게 고쳐서, Git이 어느 쪽이 맞는지 못 정하는 상태. 고장이 아니라 **사람에게 넘긴 질문**입니다.

## ⚠️ 자주 걸리는 함정

- **가지에서 일하는 걸 잊고 `main`에서 그냥 작업합니다.** 가장 흔합니다. 작업 시작 전에 `git branch`로 지금 어디인지 확인하는 걸 습관으로 만드세요.
- **가지를 만들기 전에 커밋을 안 합니다.** 안 커밋한 변경은 가지를 옮겨도 따라옵니다. 헷갈립니다. **옮기기 전에 커밋하거나 `git stash`로 치워 둡니다.**
- **가지를 몇 주씩 둡니다.** 본줄기와 멀어져서 합칠 때 충돌 범벅이 됩니다. **짧게, 자주.**
- **합친 뒤에 안 지웁니다.** 몇 달 뒤 가지가 스무 개 쌓여 뭐가 살아 있는 건지 모르게 됩니다.
- **`git switch main`을 했는데 파일이 사라졌다고 놀랍니다.** 사라진 게 아니라 **가지에 그대로 있습니다.** 다시 `git switch 가지이름`을 치면 돌아옵니다.
- **복잡한 브랜치 전략을 따라 하려 합니다.** 개발 가지·릴리스 가지·핫픽스 가지를 혼자 운영하면 **일보다 규칙 지키기에 시간이 더 듭니다.** 협업자가 생기면 그때 늘립니다.

## ⚡ 이렇게 하세요

진짜 저장소에서 한 바퀴를 **끝까지** 돌아 봅니다. 사소한 변경 하나로 충분합니다.

```bash
git switch -c 연습가지
git branch
```
> 가지를 만들고 → `* 연습가지`에 별표가 붙었는지 확인합니다.

```bash
echo "가지에서 쓴 줄" >> README.md
git add README.md && git commit -m "README에 한 줄 추가"
git push -u origin 연습가지
```
> 고치고 → 커밋하고 → GitHub에 올립니다.

GitHub 웹페이지에 가면 **「연습가지」가 목록에 보입니다.** 여기서 잠깐 멈춥니다 —
화면에 **Compare & pull request** 버튼이 떠 있을 겁니다. **지금은 누르지 않습니다.** [[07-배포PR/_스테이지|Stage 7]]에서 그 버튼을 씁니다.

```bash
git switch main
git merge 연습가지
git push
```
> 본줄기로 돌아와 → 합치고 → 올립니다.

```bash
git branch -d 연습가지
git push origin --delete 연습가지
```
> 내 컴퓨터와 GitHub 양쪽에서 가지를 지웁니다.

**가지 쓰는 습관을 AI에게 박아 둡니다.**

```
이 프로젝트의 CLAUDE.md 에 브랜치 규칙을 적어줘. 내용은 이 셋:

1. main에서 직접 작업하지 않는다. 작업마다 짧은 브랜치를 하나 만든다
2. 브랜치 이름은 무슨 일인지 알아볼 수 있게 영어 소문자와 하이픈으로 짓는다
3. 큰 변경을 시작하기 전에는 반드시 지금 어느 브랜치인지 확인하고,
   main이면 브랜치를 먼저 만들자고 나에게 말한다
```

## ✅ 됐는지 확인

- [ ] `git branch`를 쳤을 때 **지금 어느 가지에 있는지 별표로 보이나**
- [ ] 가지를 만들어 커밋하고 **`main`으로 돌아갔을 때 그 변경이 안 보이나** (안 보여야 정상)
- [ ] 합친 뒤 `main`에서 **그 변경이 보이나**
- [ ] GitHub 웹페이지의 가지 목록에서 **연습 가지가 지워졌나**
- [ ] 「본줄기를 안 건드리고 옆에서 해 본다」가 **왜 AI에게 크게 시키는 데 유리한지** 말할 수 있나
- [ ] 복잡한 가지 전략이 **여러 명일 때 쓰는 것**이라는 걸 아나
