## 왜 이걸 하나

되돌리기는 **되돌아갈 지점이 있을 때만** 됩니다. 그 지점을 만드는 게 커밋입니다.

문제는 **어떻게 나누느냐**입니다. 여기서 갈립니다.

> 오늘 로그인 화면을 고치고, 색을 바꾸고, 오타를 잡았습니다.
> 이걸 **한 번에** 저장했습니다.
> 다음 날 색이 마음에 안 들어 되돌리려 합니다.
> **→ 색만 되돌릴 방법이 없습니다.** 로그인 수정과 오타 수정까지 같이 날아갑니다.

이 절을 대충 하면 5절의 되돌리기가 **반쯤만 작동합니다.** 되돌릴 수는 있는데, 되돌리고 싶지 않은 것까지 같이 되돌아갑니다.

## 한 커밋 = 한 가지

규칙은 한 줄입니다. **하나의 커밋은 하나의 이유로 묶입니다.**

| 나쁜 예 | 좋은 예 |
|---|---|
| 「오늘 작업」 (다섯 가지가 섞임) | 「로그인 화면 여백 정리」 |
| 「수정」 | 「가입 이메일 중복 검사 추가」 |
| 「이것저것」 | 「README 오타 수정」 |

**나누는 기준을 정하는 질문 하나** — *"이걸 나중에 통째로 무를 일이 생길까?"*
답이 갈리는 지점이 커밋의 경계입니다. 로그인 수정은 무를 수 있고 오타 수정은 그럴 일이 없다면, 둘은 다른 커밋입니다.

**얼마나 자주 하나** — 「한 가지가 끝나고 돌아가는 걸 확인했을 때」입니다. 시간이 아니라 **일의 단위**입니다. 하루에 열 번도 정상이고, 큰 것 하나에 한 번도 정상입니다.

**AI에게 시킬 때는 더 중요합니다.** AI는 시키면 파일 열 개를 한 번에 고칩니다. 시키기 **전에** 커밋해 두면, 결과가 마음에 안 들 때 그 지점으로 통째로 되감으면 됩니다. **AI에게 크게 시키기 전에 커밋을 하나 찍어 두는 것** — 이게 이 장 전체의 실전 요령입니다.

## 저장하는 세 걸음

Git의 저장은 한 번에 끝나지 않고 **두 단계**입니다. 처음엔 번거롭게 느껴지지만, 이 구조 덕분에 「바꾼 것 중 일부만 저장」이 됩니다.

```bash
git status
```
> 지금 무엇이 바뀌었는지 보여 줍니다. **항상 여기서 시작합니다.**

```bash
git add 파일이름
```
> 그 파일을 「이번에 저장할 목록」에 올립니다. 전부 올리려면 `git add .` 을 씁니다.

```bash
git commit -m "가입 이메일 중복 검사 추가"
```
> 목록에 올린 것을 이름 붙여 저장합니다. `-m` 뒤의 따옴표 안이 그 이름(메시지)입니다.

```bash
git push
```
> 저장한 것을 GitHub으로 올립니다. 커밋은 **내 컴퓨터 안의 일**이고, 푸시를 해야 인터넷 창고로 갑니다.

**중요** — `git commit`과 `git push`는 다른 일입니다. 이 둘의 차이가 5절 되돌리기에서 **①②③을 가르는 기준**이 됩니다.

## 메시지 — 무엇을 왜 바꿨나

메시지를 나중의 나와 AI가 읽습니다. 그래서 **한 일의 목록**이 아니라 **이유**를 적습니다.

| ❌ 무엇을 했는지 나열 | ✅ 무엇을 왜 바꿨는지 |
|---|---|
| 「login.js, auth.js, db.js 수정」 | 「같은 이메일로 두 번 가입되던 문제 막음」 |
| 「함수 3개 추가」 | 「결제 실패했을 때 사용자에게 이유를 보여 주도록」 |
| 「스타일 변경」 | 「휴대폰에서 버튼이 잘려 크기를 키움」 |

왼쪽은 **파일을 열어 보면 어차피 아는 것**입니다. 오른쪽은 **파일을 열어도 알 수 없는 것**입니다.
기록해야 할 건 후자입니다.

## 메시지를 AI에게 쓰게 하는 법

메시지 쓰기가 귀찮아서 「수정」만 반복하게 됩니다. **AI에게 맡깁니다.**
요령은 하나 — **바뀐 것을 실제로 보여 주고 요약시킵니다.** 안 보여 주면 지어냅니다.

```bash
git diff --cached
```
> 지금 저장하려는 것이 **정확히 무엇이 바뀌었는지** 줄 단위로 보여 줍니다.

AI 대화창에 붙여넣습니다.

```
지금 저장할 변경사항을 `git diff --cached` 로 직접 읽어보고,
커밋 메시지를 한 줄로 지어줘. 조건 셋:

1. 파일 이름이나 함수 이름을 나열하지 말고, 「무엇을 왜 바꿨는지」를 써줘
2. 한글로, 50자 안쪽으로
3. 이 변경이 사실은 두 가지 이상 섞여 있으면,
   메시지를 짓지 말고 「커밋을 몇 개로 나눠야 하는지」를 먼저 알려줘

메시지만 보여주고, 커밋은 내가 확인한 다음에 해.
```

**조건 3이 진짜입니다.** AI가 "이건 세 가지가 섞였습니다"라고 말해 주면, 그때 나눕니다.
**사람은 자기가 섞은 걸 못 알아봅니다. AI는 알아봅니다.**

## 📘 말 풀이

**커밋(commit)**
지금 상태를 이름 붙여 저장하는 것. 되감기 표시를 하나 꽂는 일입니다. 커밋마다 긴 글자·숫자 줄(예: `a3f9c21…`)이 자동으로 붙는데, 이게 그 지점의 **주소**입니다. 5절에서 이 주소를 씁니다.

**스테이지(staging area) — `git add`가 하는 일**
「이번에 저장할 것」을 담아 두는 **장바구니**입니다. 바꾼 파일 다섯 개 중 셋만 담아 저장할 수 있습니다. 이 장바구니가 있어서 「한 커밋 = 한 가지」가 가능합니다.

**diff**
두 시점 사이에 **정확히 어느 줄이 바뀌었는지** 보여 주는 것. 더해진 줄 앞에 `+`, 지워진 줄 앞에 `-`가 붙습니다. AI에게 요약시킬 때 먹이는 재료가 이것입니다.

## ⚠️ 자주 걸리는 함정

- **`git add .` 을 습관적으로 씁니다.** 폴더 안의 모든 걸 담습니다. **`.env`가 딸려 들어가는 사고가 여기서 납니다.** 담은 뒤 3절의 확인 명령을 반드시 칩니다.
- **커밋만 하고 푸시를 안 합니다.** 내 컴퓨터에만 있습니다. 컴퓨터가 고장 나면 그대로 사라집니다. `git status`에 「밀지 않은 커밋이 N개 있다」는 뜻의 안내가 나옵니다.
- **하루 끝에 몰아서 한 번 커밋합니다.** 되돌릴 수 있는 단위가 「하루 통째로」가 됩니다. 되돌리기의 쓸모가 사라집니다.
- **메시지에 `수정`, `업데이트`, `ㅇㅇ`만 씁니다.** 3개월 뒤에 아무 정보도 아닙니다. 게다가 AI가 이 기록을 읽어 프로젝트를 파악하므로, 부실한 메시지는 AI의 판단도 흐립니다.
- **AI에게 diff를 안 보여 주고 메시지를 시킵니다.** 그럴듯한데 사실이 아닌 메시지가 나옵니다. 반드시 **바뀐 것을 먼저 읽히세요.**
- **커밋을 「완성했을 때만」 하는 것으로 오해합니다.** 커밋은 발표가 아니라 **되돌아올 지점 만들기**입니다. 어중간해도 돌아가면 찍어 둡니다.

## ⚡ 이렇게 하세요

파일 하나를 아무렇게나 고친 뒤 아래를 순서대로 합니다.

```bash
git status
```
> 무엇이 바뀌었는지 봅니다.

```bash
git add 파일이름
```
> 저장할 것을 장바구니에 담습니다. 한 가지씩만 담습니다.

```bash
git diff --cached --name-only | grep -iE "\.env$|token|secret|credential|\.key$|\.pem$"
```
> **3절의 확인.** 아무것도 안 나와야 다음으로 갑니다.

```bash
git diff --cached
```
> 무엇이 바뀌는지 눈으로 봅니다.

```bash
git commit -m "무엇을 왜 바꿨는지 한 줄"
```
> 이름 붙여 저장합니다.

```bash
git push
```
> GitHub으로 올립니다.

**그다음, 커밋 규칙을 프로젝트에 박아 둡니다.**

```
이 프로젝트의 CLAUDE.md 에 커밋 규칙을 적어줘. 내용은 이 셋:

1. 한 커밋 = 한 가지. 성격이 다른 변경은 절대 한 커밋에 섞지 않는다
2. 커밋 메시지는 한글로, 「무엇을 왜 바꿨는지」를 쓴다. 파일·함수 나열 금지
3. 커밋 전에 반드시 아래를 실행하고, 한 줄이라도 나오면 멈추고 물어본다
   git diff --cached --name-only | grep -iE "\.env$|token|secret|credential|\.key$|\.pem$"
```

이제 AI에게 「커밋해줘」라고만 해도 이 셋을 지킵니다.

## ✅ 됐는지 확인

- [ ] `git status`를 쳤을 때 **바뀐 파일 목록이 보이나**
- [ ] 커밋을 한 번 하고 `git log --oneline`을 쳤을 때 **내가 쓴 메시지가 보이나**
- [ ] 그 메시지가 **「무엇을 왜」로 읽히나** (「수정」이 아니라)
- [ ] GitHub 저장소 웹페이지를 새로고침했을 때 **방금 올린 것이 보이나**
- [ ] **커밋과 푸시가 다른 일**이라는 걸 아나
- [ ] AI에게 `git diff --cached`를 읽히고 메시지를 받아 본 적이 있나
