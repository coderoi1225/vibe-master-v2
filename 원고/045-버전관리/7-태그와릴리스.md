## 왜 이걸 하나

커밋이 백 개쯤 쌓이면 문제가 생깁니다. **어디가 "제대로 돌아가던 그때"인지 모릅니다.**

```
a3f9c21  로그인 여백 정리
b7d1e88  결제 오류 메시지 수정
c2e4f77  카드 크기 조정
... (아흔일곱 개 더)
```

이 중에 **「손님한테 처음 보여 준 그 상태」**가 어디인지 알 수 있나요? 못 찾습니다.

태그는 그 지점에 **깃발을 꽂는 일**입니다.
그리고 릴리스는 그 깃발에 **「이번에 뭐가 달라졌는지」 설명을 붙이는 일**입니다.

## 버전 번호 읽는 법

`1.4.2` 처럼 점으로 나뉜 세 자리를 씁니다. **자리마다 뜻이 다릅니다.**

| 자리 | 이름 | 언제 올리나 | 쉽게 말하면 |
|---|---|---|---|
| **첫 자리** (`1`.4.2) | 큰 자리 | **쓰던 방식이 깨질 때** | "예전처럼 쓰면 안 됩니다" |
| **가운데** (1.`4`.2) | 기능 자리 | **기능이 늘었을 때** (기존 건 그대로) | "새로 생긴 게 있습니다" |
| **마지막** (1.4.`2`) | 고침 자리 | **버그를 고쳤을 때** | "고장 난 걸 고쳤습니다" |

**읽는 사람 입장에서의 뜻**

| 무엇에서 무엇으로 | 받는 사람이 해야 할 일 |
|---|---|
| `1.4.2` → `1.4.3` | 없음. 그냥 받으면 됩니다 |
| `1.4.2` → `1.5.0` | 없음. 새 기능이 생겼을 뿐입니다 |
| `1.4.2` → `2.0.0` | **뭔가 바뀌었으니 확인해야 합니다** |

**앞자리가 `0`이면** (`0.3.1` 등) 「아직 정식 전」이라는 뜻입니다. 마음대로 바꿔도 되는 시기입니다.
**`1.0.0`을 붙이는 순간이 「이제 이 약속을 지키겠다」는 선언**입니다. 남에게 처음 제대로 내놓을 때 붙입니다.

## 언제 버전을 올리나 — 혼자일 때

혼자 만들 때는 이렇게 단순화합니다.

| 상황 | 어떻게 |
|---|---|
| 만드는 중, 아직 남에게 안 보여 줌 | **태그 안 붙여도 됩니다.** 커밋만 쌓습니다 |
| 남에게 처음 보여 주는 상태 | **`v0.1.0`** |
| 손님이 실제로 쓰기 시작함 | **`v1.0.0`** |
| 그 뒤 기능 하나 추가 | 가운데 올림 (`v1.1.0`) |
| 그 뒤 버그 하나 고침 | 마지막 올림 (`v1.1.1`) |

**붙이는 기준 한 줄** — *"이 상태로 되돌아올 일이 생길까?"* 그렇다면 태그를 붙입니다.
문제가 터졌을 때 **"일단 지난 태그로 되돌리자"**가 가장 빠른 복구입니다.

> 태그 이름 앞에 `v`를 붙이는 건 관례입니다. 안 붙여도 되지만, 붙이면 목록에서 한눈에 구분됩니다.

## 태그 붙이기

```bash
git tag -a v1.0.0 -m "처음 정식으로 내놓음"
```
> 지금 지점에 `v1.0.0`이라는 깃발을 꽂습니다. 따옴표 안이 그 깃발의 설명입니다.

```bash
git push origin v1.0.0
```
> 그 깃발을 GitHub에도 올립니다. **태그는 `git push`만으로는 안 올라갑니다. 따로 올려야 합니다.**

```bash
git tag
```
> 지금까지 붙인 태그 목록을 봅니다.

지난 상태로 돌아가 확인하고 싶을 때.

```bash
git switch -c 확인용 v1.0.0
```
> 그 태그 시점의 상태로 새 가지를 내서 들어갑니다. **지금 상태는 그대로 남습니다.**

## 릴리스 노트 — 버튼 하나로 나옵니다

GitHub에는 **합쳐진 작업 목록을 읽어서 릴리스 노트를 자동으로 만들어 주는 버튼**이 있습니다.
직접 쓰지 않아도 됩니다.

1. GitHub 저장소 페이지 오른쪽의 **Releases** → **Draft a new release**
2. **Choose a tag**에서 방금 올린 태그를 고릅니다
3. **Generate release notes** 버튼을 누릅니다
4. 지난 태그 이후로 합쳐진 작업들이 **목록으로 자동으로 채워집니다**
5. 맨 위에 사람이 읽을 한두 줄을 얹고 **Publish release**

**여기서 6절과 4절이 값을 합니다.** 자동 생성되는 목록은 **합쳐진 가지의 이름과 커밋 메시지**로 만들어집니다.
그동안 메시지를 「수정」「업데이트」로만 써 왔다면 **릴리스 노트도 「수정」「업데이트」가 됩니다.**
「무엇을 왜 바꿨는지」를 써 온 사람은 **여기서 공짜로 문서를 얻습니다.**

**AI에게 사람 말로 다듬게 하기**

```
아래는 GitHub이 자동 생성한 릴리스 노트야.
이걸 개발자가 아닌 사용자가 읽을 수 있게 다시 써줘.

- 맨 위에 「이번에 달라진 것」 3줄 요약
- 기술 용어는 풀어서
- 자동 생성된 원래 목록은 아래에 그대로 남겨 둬

(여기에 붙여넣기)
```

## ⚠️ 지금 넣지 않는 것 — worktree

여러 작업 폴더를 동시에 띄워 놓고 **에이전트를 둘 이상 나란히 돌리는** 격리 방식이 있습니다. `worktree`라고 부릅니다.

**지금은 넣지 않습니다.**

- **한 번에 하나씩 하면 필요가 없습니다.** 가지만 있으면 충분합니다.
- **지금 배우면 헷갈리기만 합니다.** 폴더가 여러 개로 늘어나서, 방금 익힌 「지금 어느 가지에 있나」가 「지금 어느 폴더의 어느 가지에 있나」로 복잡해집니다.
- 필요해지는 조건이 분명합니다 — **AI를 둘 이상 동시에 돌려서 서로 파일을 밟기 시작할 때**입니다. 그때 배우면 30분이면 됩니다.

**먼저 되돌리기와 가지가 손에 붙는 게 우선입니다.** 그다음에 늘립니다.

## 📘 말 풀이

**태그(tag)**
특정 커밋에 붙이는 이름표. 커밋 주소(`a3f9c21…`)는 사람이 못 외우니까 `v1.0.0` 같은 이름을 대신 붙입니다. **깃발**이라고 생각하면 됩니다. 붙인 뒤에는 움직이지 않습니다.

**릴리스(release)**
GitHub이 태그 위에 얹어 주는 **발표 페이지**. 「이번 판에서 뭐가 달라졌는지」 설명과, 필요하면 내려받을 파일이 함께 놓입니다. 태그는 Git의 기능이고 릴리스는 GitHub의 기능입니다.

**버전 번호 체계(Semantic Versioning, 줄여서 SemVer)**
「첫 자리는 깨질 때, 가운데는 기능이 늘 때, 마지막은 고칠 때」라는 **널리 쓰이는 약속**. 강제는 아니지만 이걸 따르면 남이 숫자만 보고 판단할 수 있습니다.

## ⚠️ 자주 걸리는 함정

- **태그를 만들고 `git push`만 합니다.** 안 올라갑니다. **`git push origin 태그이름`**을 따로 쳐야 합니다.
- **처음부터 `v1.0.0`을 붙입니다.** 아직 바뀔 게 많은 시기에 `1`을 붙이면 곧 `2.0.0`, `3.0.0`이 됩니다. **`v0.x`로 시작하는 게 편합니다.**
- **커밋 하나마다 태그를 붙입니다.** 깃발이 백 개면 깃발이 아닙니다. **되돌아올 만한 지점에만** 붙입니다.
- **태그 이름을 재활용합니다.** 이미 붙인 태그를 다른 커밋으로 옮기면, 그걸 받아 간 곳과 어긋납니다. **새 번호를 붙입니다.**
- **릴리스 노트를 손으로 다 씁니다.** 자동 생성 버튼을 먼저 누르고 위에 요약만 얹습니다.
- **worktree부터 배우려 합니다.** 순서가 거꾸로입니다. 되돌리기와 가지가 먼저입니다.

## ⚡ 이렇게 하세요

지금 저장소에 첫 깃발을 꽂습니다.

```bash
git switch main
git pull
```
> 본줄기로 가서 → 최신 상태를 받아 옵니다. **태그는 최신 상태에 붙여야 합니다.**

```bash
git tag -a v0.1.0 -m "처음 만든 상태"
git push origin v0.1.0
```
> 깃발을 꽂고 → GitHub에 올립니다.

```bash
git tag
```
> 목록에 `v0.1.0`이 보이면 성공입니다.

이어서 GitHub 웹페이지에서.

1. 저장소 페이지 오른쪽 **Releases** → **Draft a new release**
2. **Choose a tag** → `v0.1.0`
3. **Generate release notes** 클릭 — 목록이 자동으로 채워집니다
4. 맨 위에 한 줄 얹고 **Publish release**

마지막으로 **태그를 붙이는 기준을 프로젝트에 적어 둡니다.**

```
이 프로젝트의 CLAUDE.md 에 버전 규칙을 적어줘. 내용은 이 셋:

1. 되돌아올 만한 지점에만 태그를 붙인다. 커밋마다 붙이지 않는다
2. 첫 자리는 쓰던 방식이 깨질 때, 가운데는 기능이 늘 때, 마지막은 고쳤을 때 올린다
3. 태그를 만들면 git push origin <태그이름> 으로 따로 올려야 한다는 걸 잊지 말고 알려준다
```

## ✅ 됐는지 확인

- [ ] `git tag`를 쳤을 때 **내가 붙인 태그 이름이 나오나**
- [ ] GitHub 저장소 페이지 오른쪽에 **Releases 항목에 숫자 1이 보이나**
- [ ] 릴리스 페이지에 **자동 생성된 변경 목록이 채워져 있나**
- [ ] 「첫 자리 / 가운데 / 마지막」이 각각 **언제 올라가는지** 말할 수 있나
- [ ] 태그를 만든 뒤 **`git push origin 태그이름`을 따로 쳐야 한다**는 걸 아나
- [ ] worktree를 **지금은 안 배운다**는 걸 알고, 언제 필요해지는지 아나
