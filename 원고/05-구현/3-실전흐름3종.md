일하다 보면 결국 세 가지밖에 없습니다 — **새로 만들거나, 망가진 걸 고치거나, 오늘 한 일을 정리하거나.** 길을 셋만 정해 두면 "이번엔 뭐라고 시키지?"에 머리를 안 쓰고, 그 힘이 검증에 남습니다.

## ① 새 기능 길 여섯 걸음을 본다

| 순서 | 하는 일 | 왜 |
|---|---|---|
| 1 계획 | 무엇을 만들지 글로 ([[05-구현/1-계획먼저|1절]]) | 혼자 정한 것을 드러내려고 |
| 2 문서 | 계획을 파일로 남긴다 | 다음 세션이 이어받게 |
| 3 테스트 먼저 | "이게 되면 성공"을 먼저 정한다 | ⭐ 합격선을 AI가 못 정하게 |
| 4 구현 | 그제야 만든다 | 앞의 셋이 있으면 안 헤맨다 |
| 5 리뷰 | 새 대화에게 트집을 잡게 한다 | 짠 세션은 자기를 옹호한다 |
| 6 검증 | 내가 눈으로 본다 | "통과"는 "됐다"가 아니다 |

**3번이 자리를 옮기면 안 됩니다.** 만든 뒤에 테스트를 만들면 AI는 이미 만든 것에 맞춰 시험지를 씁니다 — 답을 보고 문제를 내는 것과 같습니다 ([[05-구현/4-테스트|4절]]).

## ② 버그 길 다섯 걸음을 본다

"이거 왜 안 되지? 고쳐 줘."라고 하면 AI는 눈에 보이는 증상만 가립니다. 사흘 뒤 같은 문제가 다른 얼굴로 돌아옵니다.

| 순서 | 하는 일 | 요령 |
|---|---|---|
| 1 증상 | 무엇을 했더니 무엇이 나왔나 | 원인을 추측해 말하지 않는다 |
| 2 분석 | AI가 관련 파일을 훑는다 | 아직 고치지 못하게 한다 |
| 3 근본 원인 | "왜 그렇게 됐나"를 한 문장으로 | ⭐ 말 못 하면 아직 모르는 것 |
| 4 재현 테스트 | 그 버그를 잡는 시험을 먼저 만든다 | 지금은 실패해야 정상 |
| 5 고치고 검증 | 그 시험이 통과하나 본다 | 통과하면 다시 안 생긴다 |

**"고쳐 줘"보다 "왜 그런지부터 알려 줘"가 빠릅니다.** 4번까지 하면 그 버그는 다시는 조용히 돌아오지 못합니다.

## ③ 마무리 길 네 걸음을 본다

그냥 창을 닫으면 오늘 배운 것이 오늘로 끝납니다. 내일의 나는 남이고, AI는 기억이 아예 없습니다.

| 순서 | 하는 일 |
|---|---|
| 1 문서 갱신 | 오늘 정한 것을 지침 파일과 문서에 반영 |
| 2 패턴 추출 | 세 번 이상 반복한 지시만 스킬로 |
| 3 커밋 | 코드와 문서를 같이 ([[045-버전관리/_스테이지|Stage 4.5]]) |
| 4 메모 | "내일은 여기서부터" 한 줄 |

**기준은 세 번입니다.** 세 번 반복했으면 규칙이지 우연이 아닙니다. 규칙이 100개가 되면 아무도 관리하지 않으니 적고 날카롭게 둡니다.

## ④ 리뷰는 새 대화에 맡긴다

같은 대화에서 "검토해 줘"라고 하면 대체로 "잘 됐습니다"가 나옵니다. 사람도 자기 글의 오타를 못 봅니다.

새 대화를 열고 **"처음 보는 코드"라고 못 박은 뒤** 시킵니다. 칭찬은 금지하고 문제만 짚게 합니다.

## ⚡ 따라 하기

1. 새 기능을 만들 때 아래를 붙이세요 — 걸음마다 멈춰야 내가 읽고 고칠 자리가 생깁니다. 계획이 오면 OK를 주고, 실패하는 테스트 화면이 보여야 다음으로 넘어갑니다.

```
새 기능을 만들 거야. 아래 여섯 걸음을 순서대로 하되, 각 걸음이 끝날 때마다 멈추고 내 확인을 받아.

만들 기능: (한 줄로)

1. 계획 — 새로 만들 파일, 고칠 파일, 네가 혼자 정한 것을 글로만. 코드 금지.
2. 문서 — 내가 OK 하면 그 계획을 docs/ 아래 파일로 저장해 줘.
3. 테스트 먼저 — "됐다"고 말할 수 있는 조건 3개를 테스트로 먼저 만들어 줘.
   지금은 실패해야 정상이야. 실패하는 걸 보여 줘.
4. 구현 — 그 테스트가 통과하도록 만들어 줘. 계획에 없는 파일은 건드리지 마.
5. 리뷰 — 바뀐 파일마다 무엇이 바뀌었는지 한국어로 요약해 줘.
6. 검증 — 내가 화면에서 눈으로 확인할 목록 3개. ○/× 로 답할 수 있게.
```

2. 버그가 나면 증상만 적어 원인부터 캐게 하세요 — 내가 원인을 추측해 말하면 AI가 그쪽만 팝니다. 근본 원인 한 문장과 확인 방법이 돌아오고, 아직 코드는 바뀌지 않아야 합니다.

```
문제가 생겼어. 아직 고치지 마. 원인부터 찾아 줘.

내가 한 일: (예 — 가입 화면에서 이메일을 넣고 '구독' 버튼을 눌렀다)
기대한 것: (예 — "구독 완료" 문구가 뜬다)
실제로 일어난 것: (예 — 화면이 하얗게 변했다)
화면에 나온 글자 그대로:
(에러 메시지를 요약하지 말고 통째로. 없으면 "없음")

1. 관련 있어 보이는 파일과 흐름을 훑어 줘
2. 근본 원인을 한 문장으로 — 확실하지 않으면 "확실하지 않다"고 말해
3. 그 원인이 맞는지 확인할 방법을 알려 줘
```

3. 원인을 확인했으면 재현 테스트부터 시키세요 — 시험지가 지키고 있어야 그 버그가 조용히 돌아오지 못합니다. 빨간불 → 고침 → 초록불 순으로 보이고, 마지막에 지침 파일에 넣을 한 줄이 옵니다.

```
원인이 맞는 걸 확인했어. 이 순서로 해 줘.

1. 이 버그를 잡아내는 테스트를 먼저 만들어 줘. 지금은 실패해야 정상이야. 실패하는 걸 보여 줘.
2. 그 다음에 고쳐 줘. 범위는 최소한으로.
3. 테스트가 통과하는 걸 보여 줘.
4. 이번 일로 알게 된 것을 지침 파일에 넣을 한 줄로 정리해 줘.
```

4. 하루를 닫을 때 아래를 붙이세요 — 오늘 배운 것을 내일의 나와 AI에게 남기기 위해서입니다. 문서 수정, 스킬 제안(세 번 반복된 것만), 커밋 메시지, "내일은 여기서부터" 한 줄이 돌아와야 합니다.

```
오늘 작업을 마무리할게.

1. 오늘 바뀐 것 중 문서나 지침 파일에 반영할 내용을 찾아 고쳐 줘
2. 오늘 내가 세 번 이상 반복한 지시가 있나? 있으면 그것만 스킬로 만들자고 제안해 줘. 두 번 이하는 제안하지 마.
3. 커밋 메시지를 한국어 한 줄로 — 무엇을 왜 바꿨는지
4. "내일은 여기서부터" 한 줄을 메모로 남겨 줘
```

5. 리뷰는 새 대화를 열고 아래를 붙이세요 — 방금 짠 세션은 자기 선택을 옹호하기 때문입니다. "OK" 한 마디이거나, 파일·위치·고칠 방법 목록과 가장 위험한 하나가 돌아와야 합니다.

```
너는 이 코드를 처음 보는 사람이야. 누가 짰는지 모르고, 칭찬할 이유도 없어.
최근에 바뀐 부분만 보고 아래 관점에서 문제만 짚어 줘.

1. 실패했을 때 사용자에게 무엇이 보이나
2. 빈 값·아주 긴 값·두 번 연속 누르기를 빠뜨리지 않았나
3. 비밀번호나 열쇠 같은 값이 밖으로 새는 곳이 있나
4. 여섯 달 뒤에 봐도 무슨 뜻인지 알 수 있나

"잘 짰다"는 평가는 쓰지 마. 문제 없으면 "OK" 한 마디만.
문제가 있으면 어느 파일 어느 부분인지와 고칠 방법을 한 줄씩. 마지막에 가장 위험한 하나를 골라 줘.
```

## ✅ 확인

- [ ] 계획이 대화가 아니라 파일로 남아 있나
- [ ] 버그를 고치기 전에 근본 원인을 한 문장으로 들었나
- [ ] 그 버그를 잡는 재현 테스트가 저장소에 남아 있나
- [ ] 리뷰를 새 대화에서 시켰나

## 📘 말 풀이

**리뷰(review)** — 만든 것을 다른 눈으로 다시 훑어 문제를 찾는 일. 여기서는 새 대화에게 시킵니다.

**근본 원인(root cause)** — 증상 말고 진짜로 그렇게 만든 이유. "화면이 하얗게 뜬다"는 증상, "구독자 목록이 비었을 때를 생각 안 했다"가 근본 원인입니다.

**스킬(skill)** — 자주 쓰는 지시를 파일 하나로 두고 이름으로 부르는 것. 만드는 법은 [[03-컨텍스트하네스/5-스킬|Stage 3]]에 있습니다.

## ⚠️ 함정

**원인을 내가 추측해서 알려 줍니다.** "아마 데이터베이스 문제 같아"라고 하면 AI는 그쪽만 팝니다. 증상만 말하세요.

**잘 되면 마무리를 건너뜁니다.** 잘 될 때 남긴 기록이 가장 값이 큽니다. 망했을 때는 기록할 정신이 없습니다.

**스킬을 욕심내서 열 개씩 만듭니다.** 세 번 반복된 것만. 나머지는 그때그때.
