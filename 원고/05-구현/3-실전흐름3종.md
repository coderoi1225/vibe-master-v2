일하다 보면 결국 세 가지밖에 없습니다.
**새로 만들거나, 망가진 걸 고치거나, 오늘 한 일을 정리하거나.**

## 왜 이걸 하나

처음 몇 주 동안 가장 지치는 것은 코딩이 아닙니다.
**"이번엔 뭐라고 시키지?"**를 매번 처음부터 생각하는 일입니다.

그래서 길을 세 개만 정해 두고 그대로 반복합니다.
길이 정해져 있으면 머리를 안 써도 되고, 머리를 안 쓰면 **검증에 쓸 힘이 남습니다.**
1인 사업에서 병목은 만드는 쪽이 아니라 보는 쪽이니까요.

이 절을 건너뛰면 매번 다른 방식으로 시키게 되고, 그러면 **왜 잘 됐는지도 왜 망했는지도 모르게 됩니다.**

## 흐름 ① 새 기능 — 계획 → 문서 → 테스트 먼저 → 구현 → 리뷰 → 검증

| 순서 | 하는 일 | 왜 여기에 있나 |
|---|---|---|
| 1 **계획** | 무엇을 만들지 글로 (절 1) | AI가 혼자 정한 것을 드러내려고 |
| 2 **문서** | 계획을 파일로 남긴다 | 대화가 사라져도 남고, 다음 세션이 이어받는다 |
| 3 **테스트 먼저** | "이게 되면 성공"을 먼저 정한다 | ⭐ 합격선을 AI가 정하지 못하게 |
| 4 **구현** | 그제야 만든다 | 앞의 셋이 있으면 여기서 헤매지 않는다 |
| 5 **리뷰** | 새 대화에게 트집을 잡게 한다 | 방금 짠 세션은 자기 선택을 옹호한다 |
| 6 **검증** | 내가 눈으로 본다 | "통과"는 "됐다"가 아니다 |

**3번이 자리를 옮기면 안 됩니다.** 만든 뒤에 테스트를 만들면 AI는 **이미 만든 것에 맞춰서** 테스트를 씁니다.
그건 시험 문제를 답 보고 만드는 것과 같습니다. 자세한 이유는 절 4에서.

**5번 리뷰는 반드시 새 대화에서.** 같은 대화에서 "검토해 줘"라고 하면 대체로 "잘 됐습니다"가 나옵니다.
사람도 자기가 쓴 글의 오타를 못 봅니다. **처음 보는 눈**이 필요합니다.

## 흐름 ② 버그 — 증상 → 분석 → 근본 원인 → 재현 테스트 → 검증

무언가 안 될 때 사람들이 가장 많이 하는 말은 이겁니다. **"이거 왜 안 되지? 고쳐 줘."**
그러면 AI는 **눈에 보이는 증상만** 가립니다. 사흘 뒤 같은 문제가 다른 얼굴로 돌아옵니다.

| 순서 | 하는 일 | 한 줄 요령 |
|---|---|---|
| 1 **증상 설명** | 무엇을 했더니 무엇이 나왔나 | 원인을 추측해서 말하지 않는다 |
| 2 **분석** | AI가 관련 파일과 흐름을 훑는다 | 아직 고치지 못하게 한다 |
| 3 **근본 원인** | "왜 그렇게 됐나"를 한 문장으로 | ⭐ 원인을 말 못 하면 아직 모르는 것 |
| 4 **재현 테스트** | 그 버그를 잡아내는 시험을 먼저 만든다 | 지금은 실패해야 정상 |
| 5 **고치고 검증** | 고친 뒤 그 시험이 통과하나 본다 | 통과하면 다시 안 생긴다 |

**"고쳐 줘"보다 "왜 그런지부터 알려 줘"가 훨씬 빠릅니다.**
그리고 4번을 하면 그 버그는 **다시는 조용히 돌아오지 못합니다.** 시험지가 지키고 있으니까요.

증상을 설명할 때 지켜야 할 것 하나 — **에러는 요약하지 말고 그대로 붙입니다.** 절 5에서 자세히.

## 흐름 ③ 마무리 — 문서 갱신 → 반복된 패턴을 스킬로

일이 끝났는데 그냥 창을 닫으면, 오늘 배운 것이 **오늘로 끝납니다.**
내일의 나는 남입니다. 그리고 **AI는 기억이 아예 없습니다.**

| 순서 | 하는 일 |
|---|---|
| 1 **문서 갱신** | 오늘 정한 것·바뀐 것을 지침 파일과 문서에 반영 |
| 2 **패턴 추출** | 오늘 세 번 이상 반복한 지시가 있으면 **스킬**로 만든다 |
| 3 **커밋** | 코드와 문서를 같이 커밋 (Stage 4.5) |
| 4 **다음 줄 메모** | "내일은 여기서부터" 한 줄 |

**기준은 3번입니다.** 같은 말을 세 번 반복했으면 그건 규칙이지 우연이 아닙니다. 그때만 스킬로 만듭니다.
한 번 겪은 일은 그냥 넘어갑니다. 규칙이 100개가 되면 아무도 관리하지 않고, 규칙끼리 싸우다가 썩습니다.
**규칙은 적고 날카롭게.**

## 📘 말 풀이

- **리뷰** — 만든 것을 다른 눈으로 다시 훑어보고 문제를 찾는 일. 여기서 말하는 리뷰는 **새 대화**에게 시키는 것입니다.
- **근본 원인** — 겉으로 보이는 증상 말고, 진짜로 그렇게 만든 이유. "화면이 하얗게 뜬다"는 증상이고, "구독자 목록이 비었을 때를 생각 안 했다"가 근본 원인입니다.
- **스킬** — 자주 쓰는 지시를 파일 하나로 만들어 두고 이름으로 부르는 것. 매번 같은 설명을 다시 쓰지 않게 해 줍니다. 만드는 법은 Stage 3에서 다뤘습니다.

## ⚠️ 자주 걸리는 함정

- **만든 뒤에 테스트를 만든다** — 이미 만든 것에 맞춘 시험지가 나옵니다. 순서를 바꾸지 마세요.
- **짠 대화에게 리뷰를 시킨다** — "잘 짰습니다"가 나옵니다. 새 대화에서, "처음 보는 코드"라고 못 박고 시킵니다.
- **원인을 내가 추측해서 알려 준다** — "아마 데이터베이스 문제 같아"라고 하면 AI는 그쪽만 팝니다. **증상만** 말하세요.
- **잘 되면 마무리를 건너뛴다** — 잘 될 때 남긴 기록이 가장 값이 큽니다. 망했을 때는 기록할 정신이 없습니다.
- **스킬을 욕심내서 열 개씩 만든다** — 세 번 반복된 것만. 나머지는 그때그때.

## ⚡ 이렇게 하세요

**① 새 기능 — 여섯 걸음을 한 번에 지시**

```
새 기능을 만들 거야. 아래 여섯 걸음을 순서대로 하되, 각 걸음이 끝날 때마다 멈추고 내 확인을 받아.

만들 기능: (한 줄로)

1. 계획 — 새로 만들 파일, 고칠 파일, 네가 혼자 정한 것을 글로만 써 줘. 코드 금지.
2. 문서 — 내가 계획에 OK 하면, 그 계획을 docs/ 아래 파일로 저장해 줘.
3. 테스트 먼저 — 이 기능이 "됐다"고 말할 수 있는 조건 3개를 테스트로 먼저 만들어 줘.
   지금은 당연히 실패해야 해. 실패하는 걸 나에게 보여 줘.
4. 구현 — 이제 그 테스트가 통과하도록 만들어 줘. 계획에 없는 파일은 건드리지 마.
5. 리뷰 — 바뀐 파일 목록과 각 파일에서 무엇이 바뀌었는지 한국어로 요약해 줘.
6. 검증 — 내가 브라우저나 화면에서 눈으로 확인할 목록 3개를 줘.
   각 항목은 ○/× 로 답할 수 있게. "잘 되는 것 같다" 같은 말 금지.
```

**② 버그 — 증상만 말하고 원인부터 캐기**

```
문제가 생겼어. 아직 고치지 마. 원인부터 찾아 줘.

내가 한 일: (예 — 가입 화면에서 이메일을 넣고 '구독' 버튼을 눌렀다)
내가 기대한 것: (예 — "구독 완료" 문구가 뜬다)
실제로 일어난 것: (예 — 화면이 하얗게 변하고 아무것도 안 나온다)
화면에 나온 글자 그대로:
(에러 메시지를 요약하지 말고 통째로 붙입니다. 없으면 "없음")

순서:
1. 관련 있어 보이는 파일과 흐름을 훑어 줘
2. 근본 원인을 한 문장으로 말해 줘 — 확실하지 않으면 "확실하지 않다"고 말해
3. 그 원인이 맞는지 확인할 방법을 알려 줘
아직 코드는 고치지 마.
```

**③ 버그 — 원인이 확인된 뒤 (재현 테스트부터)**

```
원인이 맞는 걸 확인했어. 이제 이 순서로 해 줘.

1. 이 버그를 잡아내는 테스트를 먼저 만들어 줘. 지금은 실패해야 정상이야. 실패하는 걸 보여 줘.
2. 그 다음에 고쳐 줘. 고치는 범위는 최소한으로.
3. 테스트가 통과하는 걸 보여 줘.
4. 이번 일로 알게 된 것을 한 줄로 정리해 줘 — 지침 파일에 넣을 문장으로.
```

**④ 마무리 — 하루를 닫는 한 판**

```
오늘 작업을 마무리할게.

1. 오늘 바뀐 것 중에서 문서나 지침 파일에 반영해야 할 내용을 찾아서 고쳐 줘
2. 오늘 내가 세 번 이상 반복해서 말한 지시가 있나? 있으면 그것만 스킬로 만들자고 제안해 줘.
   두 번 이하는 제안하지 마.
3. 커밋 메시지를 한국어로 한 줄 써 줘 — 무엇을 왜 바꿨는지
4. "내일은 여기서부터" 한 줄을 메모로 남겨 줘
```

**⑤ 리뷰 — 반드시 새 대화를 열고**

```
너는 이 코드를 처음 보는 사람이야. 누가 짰는지 모르고, 칭찬할 이유도 없어.
최근에 바뀐 부분만 보고 아래 관점에서 문제만 짚어 줘.

1. 실패했을 때 어떻게 되나 — 사용자에게 무엇이 보이나
2. 빈 값·아주 긴 값·두 번 연속 누르기 같은 경우를 빠뜨리지 않았나
3. 비밀번호나 열쇠 같은 값이 밖으로 새는 곳이 있나
4. 여섯 달 뒤에 봐도 무슨 뜻인지 알 수 있나

"잘 짰다"는 평가는 쓰지 마. 문제 없으면 "OK" 한 마디만.
문제가 있으면 어느 파일 어느 부분인지와 고칠 방법을 한 줄씩.
마지막에 가장 위험한 하나를 골라 줘.
```

## ✅ 됐는지 확인

- [ ] 새 기능 흐름에서 **테스트를 만들기 전에** 만들지 않았나 (순서를 지켰나)
- [ ] 계획이 **파일로 남아** 있나 (대화에만 있지 않나)
- [ ] 버그를 고치기 전에 **근본 원인을 한 문장으로** 들었나
- [ ] 그 버그를 잡는 **재현 테스트**가 지금 저장소에 남아 있나
- [ ] 리뷰를 **새 대화**에서 시켰나
- [ ] 오늘 마무리로 **문서 갱신 + 커밋**을 했나

## 🔎 더 깊이

- 이 세 흐름은 원래 개발팀이 쓰던 절차를 1인용으로 줄인 것입니다. 영어 자료에서는 **plan → docs → TDD → implement → review → verify**로 부릅니다.
- 도구에 따라 이 걸음마다 짧은 명령이 준비되어 있습니다. 앱에서 `/`를 치면 지금 쓸 수 있는 목록이 나옵니다. **없으면 위 프롬프트를 그대로 스킬로 만들면 됩니다.**
- 리뷰를 **다른 회사의 도구**에게 한 번 더 시키는 방식이 개발자들 사이에 흔합니다. 다만 그게 실제로 얼마나 이득인지는 **측정된 적이 없습니다.** 흔하다는 것과 효과가 증명됐다는 것은 다릅니다. 이 이야기는 Stage 7에서 정직하게 다룹니다.
