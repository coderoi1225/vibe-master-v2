"테스트는 개발자가 하는 거 아닌가요?"
아닙니다. **코드를 못 읽는 사람일수록 더 필요합니다.**

우리는 코드를 못 읽습니다. 그래서 AI가 "다 됐습니다"라고 하면 확인할 방법이 없습니다.
매번 브라우저를 열어서 하나하나 눌러 볼 수도 있습니다. 처음 며칠은 그렇게 합니다.
그런데 기능이 다섯 개, 열 개가 되면 **매번 열 군데를 눌러 볼 수 없습니다.**

테스트는 그 확인을 **기계가 대신하게 만드는 것**입니다.

이 절을 건너뛰면 이런 일이 생깁니다.
새 기능을 넣었더니 **어제까지 잘 되던 가입 화면이 조용히 죽습니다.**
AI는 그걸 모릅니다. 나도 모릅니다. 손님이 압니다.

## ① AI가 속도를 올리면 불안정성도 같이 오른다

이게 이 절의 핵심 문장입니다.

AI는 **증폭기**입니다. 잘 정리된 곳에서는 좋은 것을 크게 만들고,
어수선한 곳에서는 **어수선함을 크게 만듭니다.**

예전에는 하루에 파일 두 개를 고쳤습니다. 뭐가 깨졌는지 감으로 알았습니다.
지금은 한 시간에 파일 열 개가 바뀝니다. **감으로는 못 따라갑니다.**

그래서 속도가 올라간 만큼 **자동으로 확인해 주는 장치**가 있어야 합니다.
없으면 증폭되는 것은 생산성이 아니라 혼돈입니다.

> 참고로, AI 도구의 이득은 처음부터 곧장 오르지 않습니다.
> **처음에는 오히려 떨어졌다가 나중에 오릅니다.** 배우는 값과 어수선함을 치우는 값이 먼저 나가기 때문입니다.
> 첫 주에 "이거 더 느린데?"라고 느끼는 건 정상입니다. 그 구간을 테스트로 건너갑니다.

## 📘 말 풀이

- **테스트** — 이게 여전히 잘 도는지 **기계가 대신 확인해 주는 것**. 사람이 매번 손으로 눌러 보는 대신, 명령 한 줄로 전부 확인합니다. 통과하면 초록, 깨지면 빨강.
- **핵심 흐름** — 손님이 돈을 내거나 서비스를 쓰기 위해 반드시 지나가는 길. 예를 들어 "가입 → 메일 받기 → 수신 거부"가 하나의 핵심 흐름입니다.
- **실패하는 테스트 먼저** — 만들기 전에 시험지를 먼저 쓰는 방식. 시험지는 처음엔 당연히 빨간불입니다. 그 빨간불이 초록이 되면 다 된 것입니다.

## ② 전부 덮으려 하지 마세요 — 핵심 흐름 3~5개면 충분합니다

여기서 대부분이 두 번째로 망합니다. **"제대로 하려면 다 덮어야지"**라고 생각하다가 시작도 못 합니다.

1인이 지킬 수 있는 선은 이 정도입니다.

| 개수 | 무엇을 거나 | 예시 (뉴스레터 서비스) |
|---|---|---|
| 1 | 손님이 **들어오는** 길 | 이메일을 넣고 구독 버튼을 누르면 구독자로 저장된다 |
| 2 | 손님이 **값을 받는** 길 | 발송을 누르면 구독자에게 메일이 나간다 |
| 3 | 손님이 **나가는** 길 | 수신 거부를 누르면 다음부터 안 온다 |
| 4 (있으면) | **돈이 오가는** 길 | 결제하면 유료 구독자가 된다 |
| 5 (있으면) | **잘못 눌렀을 때** | 이메일 형식이 틀리면 친절한 안내가 뜬다 |

이 다섯이 초록이면 서비스는 살아 있는 것입니다. 나머지가 깨져도 손님은 대체로 모릅니다.
**커버리지 90% 같은 목표는 1인에게 과합니다.** 회사에서도 그건 팀이 있어야 지킵니다.

## ③ 실패하는 테스트를 먼저 쓰는 게 왜 AI에게 특히 잘 맞나

이유는 세 가지입니다.

**① 합격선을 AI가 정하지 못하게 됩니다.**
만든 뒤에 테스트를 만들라고 하면 AI는 **이미 만든 것에 맞춰서** 시험지를 씁니다.
답을 보고 문제를 내는 것과 같습니다. 100점은 나오지만 아무 의미가 없습니다.

**② AI에게 "끝"을 알려 줄 수 있습니다.**
AI는 "이 정도면 됐다"를 스스로 판단하면 대체로 너무 일찍 멈추거나 너무 멀리 갑니다.
빨간불이 초록으로 바뀌는 순간이 **다툴 여지 없는 끝**입니다.

**③ 코드를 못 읽어도 대화할 수 있습니다.**
"3번 테스트가 아직 빨간불이야"라고만 말하면 AI가 알아서 그 부분을 팝니다.
코드 이야기를 한 마디도 안 하고 방향을 잡을 수 있습니다. 비개발자에게 이게 가장 큽니다.

**한 가지 주의** — 테스트가 초록이라고 "됐다"는 뜻은 아닙니다.
초록불은 **"안 터졌다"**만 말합니다. **"손님에게 메일이 갔다"**는 말해 주지 않습니다.
그래서 절 6에서 **내 눈으로 보는 확인**을 한 겹 더 얹습니다.

## ⚠️ 함정

- **전부 덮으려다 하나도 못 만든다** — 3개로 시작합니다. 사고가 날 때마다 하나씩 늘립니다. 그러면 시험지가 **내가 실제로 겪은 실패의 역사**가 됩니다.
- **만든 다음에 테스트를 만든다** — 순서가 뒤집히면 시험지가 아니라 도장이 됩니다.
- **실패하는 걸 안 보고 넘어간다** — 처음에 빨간불을 **눈으로 확인**해야 합니다. 안 그러면 아무것도 확인하지 않는 가짜 테스트가 통과하고 있는 걸 모릅니다.
- **"잘 되는지" 같은 애매한 기준을 쓴다** — ○/×로 답할 수 있어야 테스트입니다.
- **깨진 테스트를 지워서 초록으로 만든다** — 가장 위험한 습관입니다. 깨진 테스트는 **고쳐야 할 것을 알려 주는 알람**입니다. 알람을 끄지 마세요.
- **실제 메일이 진짜로 나가는 테스트를 만든다** — 테스트는 하루에 수십 번 돕니다. 실제 발송·실제 결제는 **가짜로 바꿔서** 테스트합니다. AI에게 "실제로 보내지 말고 흉내만 내게 해 줘"라고 말하면 됩니다.

## ⚡ 따라 하기

**① 핵심 흐름 3개 고르기 — 코드 이야기 없이**

```
나는 코드를 못 읽어. 지금 만들고 있는 서비스에서
"이게 깨지면 손님이 바로 알아채는" 핵심 흐름 3개를 골라 줘.

조건:
- 손님 입장에서 쓴다. "가입 → 메일 받기 → 수신 거부" 같은 식으로.
- 각 흐름마다 "무엇을 하면 무엇이 나와야 하는가"를 한 줄씩.
- 기준은 ○/× 로 답할 수 있게. "잘 된다" 같은 표현 금지.
- 3개를 넘기지 마. 지금은 적게 시작하는 게 맞아.
```

**② 실패하는 테스트를 먼저 만들게 하기**

```
방금 고른 핵심 흐름 3개를 테스트로 만들어 줘. 아직 기능은 만들지 마.

조건:
- 지금은 3개 다 실패해야 정상이야. 실패하는 걸 나에게 직접 보여 줘.
- 실제로 메일을 보내거나 결제를 하지 마. 흉내만 내게 만들어 줘.
- 테스트 이름은 한국어로, 무엇을 재는지 읽으면 알 수 있게.
- 마지막에 "테스트 돌리는 명령 한 줄"을 알려 줘. 그걸 내가 외울 거야.
```

**③ 초록으로 만들기**

```
이제 이 테스트 3개가 통과하도록 만들어 줘.

- 테스트를 고쳐서 통과시키지 마. 기능을 만들어서 통과시켜.
- 하나씩 해. 1번이 초록이 되면 멈추고 나에게 보여 줘. 그 다음에 2번.
- 다 끝나면 테스트 결과 화면을 그대로 보여 줘.
```

**④ 사고가 날 때마다 한 개씩 늘리기**

```
방금 이런 문제를 겪었어: (무슨 일이 있었는지 한 줄)

이 문제가 다시 생기면 바로 빨간불이 뜨도록 테스트를 하나만 추가해 줘.
- 기존 테스트는 건드리지 마
- 이 테스트가 원래 문제 상황에서 실패하는지 먼저 확인시켜 줘
```

**⑤ 매번 돌리는 습관 만들기 — 하루 두 번**

```
아침에 작업 시작할 때, 그리고 커밋하기 직전에 테스트를 돌려 줘.
빨간불이 하나라도 있으면 새 작업을 시작하지 말고 나에게 먼저 알려 줘.
```

## ✅ 확인

- [ ] **테스트가 하나라도 도나** (명령 한 줄로 실행되나)
- [ ] 그 테스트를 **만들기 전에** 만들었나 (순서를 지켰나)
- [ ] 처음에 **빨간불을 눈으로** 봤나
- [ ] 지금 화면에 **초록불**이 보이나
- [ ] 테스트가 **핵심 흐름 3~5개**에 걸려 있나 (전부 덮으려 하지 않았나)
- [ ] 테스트가 **실제로 메일을 보내거나 결제를 하지는** 않나
- [ ] 테스트 돌리는 명령을 **내가 외우고 있나**

## 🔎 더 깊이

- 실패하는 테스트를 먼저 쓰는 방식은 영어로 **TDD (test-driven development)**라고 부릅니다. 이 단어로 찾으면 자료가 아주 많습니다.
- 손님이 실제로 화면을 누르는 것까지 흉내 내는 테스트는 **E2E (end-to-end) 테스트**라고 합니다. 핵심 흐름 3~5개는 여기에 거는 것이 가장 값이 큽니다.
- "AI가 속도를 올리면 불안정성도 같이 오른다"는 것은 매년 나오는 개발 현장 조사에서 반복해서 관찰되는 내용입니다. 검색할 말 — **DORA** 보고서.
- 커밋할 때마다 테스트를 자동으로 돌리게 만들 수 있습니다. 그건 Stage 7(배포)에서 다룹니다. 지금은 **손으로 돌리는 것으로 충분합니다.**

> **Stage 6에서 진짜 데이터베이스를 붙이면**, 이 테스트가 그대로 "데이터베이스 연결이 살아 있나"를 지키는 파수꾼이 됩니다. 그때 새로 만들지 않아도 되게, 지금 이름을 잘 지어 두세요.
