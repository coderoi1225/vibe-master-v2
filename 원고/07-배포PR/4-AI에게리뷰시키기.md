## 왜 이걸 하나

앞 절의 검사 넷은 **기계가 답을 아는 것**만 잡습니다.
문법이 틀렸나, 열쇠가 섞였나, 테스트가 떨어졌나. 여기까지는 확실합니다.

그런데 다음 같은 것은 못 잡습니다.

- 로그인 실패 횟수를 세는 곳을 지웠는데, 테스트에 그게 없어서 초록불이다
- 사용자 목록을 불러오는데 **남의 것까지** 딸려 온다
- 결제가 실패했을 때 화면에는 "성공"이 뜬다

전부 **문법은 멀쩡하고 테스트는 통과**합니다. 사람이 봐야 보이는 것들입니다.
그런데 볼 사람이 나뿐입니다. 그리고 **내가 만든 것을 내가 보면 잘 안 보입니다.**

## 실리콘밸리 원칙 — 합치기 전에 둘

큰 회사의 코드 리뷰 문화에서 1인이 훔쳐 쓸 수 있는 것은 딱 둘입니다.

| 무엇 | 어떻게 |
|---|---|
| **① AI에게 바뀐 부분을 리뷰시킨다** | PR의 빨간 줄·초록 줄만 따로 떼어 다른 눈에게 보인다 |
| **② 하루 묵힌다** | 급하지 않은 변경은 다음 날 아침에 다시 보고 병합한다 |

②를 우습게 볼 게 아닙니다. 돈이 안 들고, 설치가 필요 없고,
**어제의 나와 오늘의 나는 실제로 다른 사람입니다.**
밤에 "완벽하다" 했던 것이 아침에 보면 이상한 경우가 흔합니다.

### 왜 이 둘밖에 없나 — 정직하게

회사에서 코드 리뷰가 주는 이득은 크게 둘입니다.

1. **결함을 찾는다**
2. **사람들 사이에 지식이 옮겨 간다** — 남의 코드를 읽으며 팀이 서로를 배운다

**혼자면 2번은 통째로 불가능합니다.** 옮겨 갈 상대가 없습니다.
그래서 1인이 복제할 수 있는 건 1번뿐이고, 이 절은 **그 절반을 복제하는 방법**입니다.
"리뷰를 하면 회사처럼 된다"가 아니라 **"절반만 가져온다"**가 정직한 표현입니다.

## ⚠️ 정직하게 — 효과는 통념이지 측정된 사실이 아닙니다

"한 도구로 짜고 다른 도구로 리뷰한다"는 방식은 지금 매우 흔합니다.
그런데 **이 방식이 실제로 얼마나 이득인지 측정한 자료는 찾지 못했습니다.**

| | |
|---|---|
| **흔한가** | ✅ 흔합니다. 개발자 설문에서 두 도구의 사용률이 높고, 저장소에 두 도구용 지침 파일을 함께 둔 사례가 십수만 건 규모로 확인됩니다 |
| **효과가 실측됐나** | ❌ **없습니다.** 이 방식을 다룬 글들은 전부 논증이지 실험이 아닙니다 |
| **찬성 증언** | *"한 도구가 세운 계획을 다른 도구에 리뷰시키면 항상 뭔가를 찾아낸다"* |
| **반대 증언** | *"큰 문제를 잡는 걸 본 적이 없다. 어차피 만들면서 해결될 것만 지적한다"* |

그리고 **오히려 반대 방향을 가리키는 연구**가 하나 있습니다.
모델이 유능해질수록 **서로의 오류가 닮아 간다**는 결과입니다.
그게 사실이라면 "AI를 둘 쓰면 안전망이 두 겹"이라는 가정은 **오히려 약해집니다.**
둘째 눈이 첫째 눈과 같은 곳에서 같이 틀리기 때문입니다.

> `[확인 필요]` — 이 연구는 2025년 2월에 나온 것이라, 지금의 도구들에 그대로 적용되는지는 확인하지 못했습니다.

**그래서 이 절의 표현은 이겁니다** —
*"이렇게 하면 좋아집니다"*가 아니라
**"많은 개발자가 이렇게 합니다. 다만 얼마나 이득인지 측정된 적은 없습니다."**

시간이 아깝다고 느끼면 **②(하루 묵히기)만 해도 됩니다.** 그건 공짜입니다.

## ⭐ 왜 리뷰는 다른 도구로 하나 — 실제 이유는 성능이 아니라 요금제입니다

"짜는 건 A, 리뷰는 B"라는 말을 여기저기서 보게 됩니다.
성능 차이 때문이라고 짐작하기 쉬운데, **1인에게는 다른 이유가 더 큽니다.**

| | 짜는 도구(Claude Code) | 리뷰 도구(코덱스) |
|---|---|---|
| 내 컴퓨터에서 리뷰 명령 | ✅ 개인도 가능 | ✅ |
| **PR 화면에 자동으로 붙는 리뷰** | ❌ **팀·기업 요금제 전용** | ✅ **개인 유료 플랜에서 가능** |

**Claude Code의 관리형 깃허브 리뷰는 팀·기업 요금제 전용이라 1인은 못 씁니다.**
개인 요금제로는 **내 컴퓨터에서 명령으로 부르는 리뷰**만 됩니다.
반면 **코덱스의 깃허브 PR 리뷰는 개인 유료 플랜에서 됩니다.**

이게 "리뷰는 코덱스"라는 패턴이 퍼진 **실제 이유로 보입니다.**
성능이 더 좋아서가 아니라, **1인에게 그 문이 열려 있어서**입니다.
(구체적인 요금제 이름과 값은 6개월이면 낡습니다 → 부록의 「버전과 값」)

**그래서 순서는 이렇습니다.**

```
Claude Code 로 짠다  →  내 컴퓨터에서 자체 점검 한 번
                       →  PR을 연다
                       →  거기서 다른 도구가 리뷰를 붙인다
                       →  하루 묵힌다
                       →  병합
```

**두 도구를 동시에 켜 두고 같은 저장소를 돌리지 않습니다.**
성능 문제가 아니라 **안전** 문제입니다. 도구를 둘 쓰면 위험이 더해지는 게 아니라 곱해집니다 —
설정 파일에 쓸 수 있는 권한은 곧 코드를 실행할 수 있는 권한이고,
**가장 약한 하나가 나머지 전부의 통로**가 됩니다. **순차로 씁니다.**

## 가장 저항이 적은 길 — PR 앱을 하나 붙인다

터미널도 두 번째 구독도 부담스러우면, **PR에 앱 하나를 붙이는 방법**이 있습니다.
설치하면 그때부터 PR을 열 때마다 **알아서 댓글로 리뷰를 답니다.** 내가 부를 필요가 없습니다.

| 도구 | 특징 |
|---|---|
| **CodeRabbit** | 개인 저장소에 무료 등급이 있어 **비개발자 1인의 저항이 가장 적습니다** |
| **GitHub Copilot code review** | 이미 쓰고 있으면 바로 켜집니다. 다만 무료 범위가 **사용량으로 제한**돼 금방 소진됩니다 |

**한 저장소에 리뷰 앱을 둘 이상 붙이지 않습니다.** 댓글이 두 배가 되고 읽지 않게 됩니다.

## 📘 말 풀이

**코드 리뷰(code review)**
합치기 전에 **다른 눈으로 변경을 훑는 절차**. 회사에서는 동료가 하고, 1인에게는 AI와 하루의 시차가 그 자리를 대신합니다.

**디프(diff, 바뀐 부분)**
이전과 지금의 **차이만 뽑아낸 것**. PR 화면의 빨간 줄(지운 것)·초록 줄(더한 것)이 그것입니다.
리뷰는 전체 코드가 아니라 이것만 봅니다.

**리뷰 앱(PR 앱)**
저장소에 한 번 설치해 두면 **PR이 열릴 때마다 자동으로 붙어 댓글을 다는 프로그램.**
내가 부르지 않아도 알아서 옵니다.

## ⚠️ 자주 걸리는 함정

- **AI 리뷰를 자동 병합의 근거로 삼는다** — 리뷰는 **참고 의견**이지 통과 도장이 아닙니다. 문을 지키는 건 앞 절의 검사입니다.
- **지적 스무 개를 다 고친다** — AI 리뷰는 **사소한 것을 많이** 답니다. 다 고치면 PR이 세 배로 커지고, 그러면 되돌리기 어려워집니다. **지금 사용자에게 보이는 문제만** 고치고 나머지는 다음 PR로 미룹니다.
- **AI가 "고쳐 줄까요?" 하는 대로 다 맡긴다** — 리뷰하러 온 도구가 코드를 고치기 시작하면 리뷰가 아니라 새 작업이고, 그건 다시 리뷰받지 않은 코드입니다.
- **리뷰 도구에 저장소 전체 쓰기 권한을 준다** — 읽기와 댓글 권한이면 충분합니다. 8절의 「에이전트 둘의 법칙」과 이어집니다.
- **비공개 저장소에 앱을 붙이면서 뭘 보내는지 안 본다** — 코드가 밖으로 나갑니다. 개인정보가 든 코드면 한 번 더 생각합니다.
- **하루 묵히기를 안 한다** — 둘 중에 공짜인 쪽을 먼저 버립니다. 순서가 거꾸로입니다.

## ⚡ 이렇게 하세요

**1) 먼저 내 컴퓨터에서 1차 자체 점검을 합니다.** 바뀐 부분만 뽑아서 물어봅니다.

```bash
# 본줄기와 지금 가지의 차이만 파일로 뽑는다
git diff origin/main...HEAD > /tmp/바뀐부분.diff
wc -l /tmp/바뀐부분.diff        # 500줄이 넘으면 PR을 쪼갠다
```

**2) 이 프롬프트를 씁니다.** 그냥 "리뷰해 줘"라고 하면 칭찬만 돌아옵니다.

```
아래는 내 PR의 바뀐 부분(diff)이다. 나는 비개발자이고 이 서비스를 혼자 운영한다.

칭찬은 하지 마라. 다음 넷만, 심각한 순서로 최대 5개까지 지적해라.
 ① 사용자 데이터가 남에게 새는 자리
 ② 돈·결제가 잘못 처리되는 자리
 ③ 실패했을 때 화면에 성공처럼 보이는 자리
 ④ 시키지 않았는데 함께 바뀐 곳 (왜 바뀌었는지 설명 못 하면 그것도 지적)

각 항목은 이 형식으로:
 - 파일:줄번호
 - 무슨 일이 벌어지나 (한 줄, 쉬운 말로)
 - 이걸 눈으로 확인하려면 어디를 눌러 보면 되나
확실하지 않으면 "추측"이라고 먼저 밝혀라. 없으면 "없음"이라고만 답해라.

(여기에 바뀐부분.diff 를 붙여넣기)
```

**3) PR 화면에 붙는 리뷰를 하나 답니다.** 둘 중 하나만 고릅니다.

```
[길 A — 리뷰 앱] GitHub Marketplace 에서 CodeRabbit 설치
    → 저장소 하나만 선택 (전체 계정 허용하지 않기)
    → 권한은 읽기 + PR 댓글 까지만
    → 다음 PR부터 자동으로 댓글이 달린다

[길 B — 이미 ChatGPT를 쓰고 있다면] 코덱스를 깃허브 계정에 연결
    → 저장소 하나만 선택
    → PR 화면에서 리뷰를 요청한다
```

**이미 ChatGPT를 쓰고 있다면 길 B의 한계비용이 0**이라 계산이 달라집니다.
쓰고 있지 않다면 **리뷰 하나 때문에 구독을 새로 시작하지는 않습니다.** 길 A로 갑니다.

**4) 하루 묵힙니다.** 급하지 않은 PR은 그날 병합하지 않습니다.

```markdown
<!-- PR 본문 맨 아래에 한 줄 -->
묵힘: 2026-09-10 아침에 다시 보고 병합
```

**5) 아침에 다시 열어서, 자기 PR을 스스로 읽고 병합합니다.**

## ✅ 됐는지 확인

- [ ] PR 화면에 **내가 부르지 않아도 리뷰 댓글이 붙었나**
- [ ] 그 리뷰에서 **실제로 고칠 것을 하나라도 찾았나** (못 찾았어도 정상입니다 — 위 표를 다시 보세요)
- [ ] 지적 전부가 아니라 **골라서 고쳤나**
- [ ] **하루 묵혔다가 병합한 PR이 한 건이라도 있나**
- [ ] 리뷰 도구의 권한이 **읽기와 댓글까지로 제한**돼 있나
- [ ] 두 도구를 **동시에 켜 두고** 같은 저장소를 돌리고 있지는 않나
