앞 절의 검사 넷은 기계가 답을 아는 것만 잡습니다. 문법은 멀쩡하고 테스트는 통과하는데 **사람이 봐야 보이는 것**이 남고, 볼 사람이 나뿐입니다.

## ① 검사가 못 잡는 것을 본다

- 로그인 실패 횟수를 세는 곳을 지웠는데, 테스트에 그게 없어서 초록불이다
- 사용자 목록을 불러오는데 남의 것까지 딸려 온다
- 결제가 실패했을 때 화면에는 «성공»이 뜬다

전부 문법은 멀쩡하고 테스트는 통과합니다. 그리고 **내가 만든 것을 내가 보면 잘 안 보입니다.**

## ② 합치기 전에 둘을 챙긴다

큰 회사의 코드 리뷰 문화에서 1인이 가져올 수 있는 것은 딱 둘입니다.

| 무엇 | 어떻게 |
|---|---|
| AI에게 바뀐 부분을 리뷰시킨다 | PR의 빨간 줄·초록 줄만 따로 떼어 다른 눈에게 보인다 |
| 하루 묵힌다 | 급하지 않은 변경은 다음 날 아침에 다시 보고 병합한다 |

둘째를 우습게 볼 게 아닙니다. 돈이 안 들고 설치가 필요 없고, 어제의 나와 오늘의 나는 실제로 다른 사람입니다. 회사 리뷰의 이득은 «결함을 찾는다»와 «사람들 사이에 지식이 옮겨 간다» 둘인데, 혼자면 후자는 통째로 불가능하니 이 절은 **절반만 가져오는 방법**입니다.

그리고 정직하게 — 효과는 통념이지 측정된 사실이 아닙니다. «한 도구로 짜고 다른 도구로 리뷰한다»는 방식은 매우 흔하고 저장소에 두 도구용 지침 파일을 함께 둔 사례가 십수만 건 규모로 확인되지만, 실제로 얼마나 이득인지 측정한 자료는 찾지 못했습니다. 오히려 모델이 유능해질수록 서로의 오류가 닮아 간다는 연구가 하나 있어, «AI를 둘 쓰면 안전망이 두 겹»이라는 가정은 약해집니다.

> `[확인 필요]` — 이 연구는 2025년 2월에 나온 것이라, 지금의 도구들에 그대로 적용되는지는 확인하지 못했습니다.

그래서 이 절의 표현은 «이렇게 하면 좋아집니다»가 아니라 **«많은 개발자가 이렇게 합니다. 다만 얼마나 이득인지 측정된 적은 없습니다.»**입니다. 시간이 아깝다고 느끼면 하루 묵히기만 해도 됩니다.

## ③ 왜 다른 도구로 하나 본다

«짜는 건 A, 리뷰는 B»라는 말을 여기저기서 보게 됩니다. 성능 차이 때문이라고 짐작하기 쉬운데, 1인에게는 **요금제**가 더 큰 이유입니다.

| | 짜는 도구(Claude Code) | 리뷰 도구(코덱스) |
|---|---|---|
| 내 컴퓨터에서 리뷰 명령 | 개인도 가능 | 가능 |
| PR 화면에 자동으로 붙는 리뷰 | 팀·기업 요금제 전용 | 개인 유료 플랜에서 가능 |

Claude Code의 관리형 깃허브 리뷰는 팀·기업 요금제 전용이라 1인은 못 쓰고, 코덱스의 깃허브 PR 리뷰는 개인 유료 플랜에서 됩니다. 성능이 더 좋아서가 아니라 1인에게 그 문이 열려 있어서 «리뷰는 코덱스» 패턴이 퍼진 것으로 보입니다. (요금제 이름과 값은 부록의 「버전과 값」)

```
Claude Code 로 짠다  →  내 컴퓨터에서 자체 점검 한 번
                       →  PR을 연다
                       →  거기서 다른 도구가 리뷰를 붙인다
                       →  하루 묵힌다
                       →  병합
```

두 도구를 동시에 켜 두고 같은 저장소를 돌리지 않습니다. 설정 파일에 쓸 수 있는 권한은 곧 코드를 실행할 수 있는 권한이라 가장 약한 하나가 나머지 전부의 통로가 됩니다. 순차로 씁니다.

## ④ 리뷰를 하나 붙인다

터미널도 두 번째 구독도 부담스러우면 PR에 **앱 하나**를 붙입니다. 설치하면 PR을 열 때마다 알아서 댓글로 리뷰를 달고, 내가 부를 필요가 없습니다.

| 도구 | 특징 |
|---|---|
| CodeRabbit | 개인 저장소에 무료 등급이 있어 비개발자 1인의 저항이 가장 적습니다 |
| GitHub Copilot code review | 이미 쓰고 있으면 바로 켜집니다. 무료 범위가 사용량으로 제한돼 금방 소진됩니다 |

한 저장소에 리뷰 앱을 둘 이상 붙이지 않습니다. 댓글이 두 배가 되고 읽지 않게 됩니다.

## ⑤ 하루 묵히고 골라 고친다

AI 리뷰는 사소한 것을 많이 답니다. 지적 스무 개를 다 고치면 PR이 세 배로 커져서 되돌리기 어려워지니, **지금 사용자에게 보이는 문제만** 고치고 나머지는 다음 PR로 미룹니다. 무엇을 고치고 무엇을 안 고칠지는 사람이 정합니다.

## ⚡ 따라 하기

1. 본줄기와 지금 가지의 차이만 파일로 뽑으세요 — 리뷰는 전체 코드가 아니라 바뀐 부분만 봅니다. 500줄이 넘으면 PR을 쪼갭니다.

```bash
git diff origin/main...HEAD > /tmp/바뀐부분.diff
wc -l /tmp/바뀐부분.diff        # 500줄이 넘으면 PR을 쪼갠다
```

2. 이 프롬프트로 내 컴퓨터에서 1차 점검을 시키세요 — 그냥 «리뷰해 줘»라고 하면 칭찬만 돌아옵니다. 답이 «없음»이거나 파일:줄번호가 붙은 지적 다섯 개 안으로 옵니다.

```
아래는 내 PR의 바뀐 부분(diff)이다. 나는 비개발자이고 이 서비스를 혼자 운영한다.

칭찬은 하지 마라. 다음 넷만, 심각한 순서로 최대 5개까지 지적해라.
 ① 사용자 데이터가 남에게 새는 자리
 ② 돈·결제가 잘못 처리되는 자리
 ③ 실패했을 때 화면에 성공처럼 보이는 자리
 ④ 시키지 않았는데 함께 바뀐 곳 (왜 바뀌었는지 설명 못 하면 그것도 지적)

각 항목은 이 형식으로:
 - 파일:줄번호
 - 무슨 일이 벌어지나 (한 줄, 쉬운 말로)
 - 이걸 눈으로 확인하려면 어디를 눌러 보면 되나
확실하지 않으면 "추측"이라고 먼저 밝혀라. 없으면 "없음"이라고만 답해라.

(여기에 바뀐부분.diff 를 붙여넣기)
```

3. PR 화면에 붙는 리뷰를 하나 다세요 — 둘 중 하나만 고릅니다. 이미 ChatGPT를 쓰고 있으면 길 B의 추가 비용이 없고, 아니면 리뷰 하나 때문에 구독을 새로 시작하지 말고 길 A로 갑니다. 다음 PR부터 댓글이 자동으로 달립니다.

```
[길 A — 리뷰 앱] GitHub Marketplace 에서 CodeRabbit 설치
    → 저장소 하나만 선택 (전체 계정 허용하지 않기)
    → 권한은 읽기 + PR 댓글 까지만
    → 다음 PR부터 자동으로 댓글이 달린다

[길 B — 이미 ChatGPT를 쓰고 있다면] 코덱스를 깃허브 계정에 연결
    → 저장소 하나만 선택
    → PR 화면에서 리뷰를 요청한다
```

4. 급하지 않은 PR은 그날 병합하지 말고 본문 맨 아래에 한 줄을 남기세요 — 내일 아침의 내가 다른 눈이 됩니다.

```markdown
<!-- PR 본문 맨 아래에 한 줄 -->
묵힘: 2026-09-10 아침에 다시 보고 병합
```

5. 아침에 다시 열어 자기 PR을 스스로 읽고, 리뷰 지적 중 고칠 것만 골라 고친 뒤 병합하세요 — 다 고치는 것이 잘하는 게 아닙니다.

### 이렇게 해 봤습니다 — 2026-09-10 · 실제로 시켜 봤습니다

이 교재를 굽는 스크립트(`발행/build.py`, 400줄 남짓)를 다른 도구에 읽기 전용으로 걸고 *"진짜 문제만 심각한 순서로 5개까지, 칭찬은 쓰지 마"* 라고 시켰습니다. 다섯 개를 짚었고, 하나씩 확인해 보니 이랬습니다.

| 지적 | 확인 결과 |
|---|---|
| 한글 주소가 인코딩돼 돌아와 일부 장이 목차로 튕긴다 | 진짜였습니다. 아래 참고 |
| 코드 복사 버튼의 글자가 복사한 코드에 섞인다 | 진짜였습니다. 프롬프트를 복사하면 끝에 「복사」가 붙습니다 |
| 제목을 안 적은 절이 엉뚱한 파일 이름을 제목으로 쓴다 | 진짜였습니다. 고칠 때 실수한 자리를 정확히 짚었습니다 |
| 절 번호가 겹치면 읽음 표시가 섞인다 | 맞지만 드문 경우. 그래도 고쳤습니다 |
| 원고에 HTML을 넣으면 그대로 실행된다 | 사실이지만 안 고쳤습니다. 아래 참고 |

가장 큰 것 하나 — 「부록」과 「업무 자동화」처럼 이름이 한글인 장을 누르면 전체 목차로 튕겼습니다. 주소창이 한글을 `%EB%B6%80...` 로 바꿔 돌려주는데 코드가 그걸 원래 글자와 비교하고 있었습니다. **이건 원고를 아무리 읽어도 안 나옵니다** — 코드를 읽어야 나오는 종류입니다.

안 고친 것도 하나 있습니다. 원고에 HTML을 적으면 그대로 실행된다는 지적은 사실입니다. 다만 이 교재는 내가 쓴 글을 내가 굽는 구조라, 위험을 만들 사람이 나뿐입니다. 막으려면 검사 도구를 하나 얹어야 하는데 그러면 절 사이 링크까지 지워집니다. 그래서 알고 두기로 했습니다. 다섯 중 셋을 고쳤고 하나는 알고 넘어갔습니다 — 다만 이건 한 번의 사례이지 «효과 측정»이 아닙니다. 흔한 방법이고, 얼마나 이득인지는 아직 측정된 적이 없습니다.

## 📘 말 풀이

**코드 리뷰(code review)** — 합치기 전에 다른 눈으로 변경을 훑는 절차. 회사에서는 동료가 하고, 1인에게는 AI와 하루의 시차가 그 자리를 대신합니다.

**디프(diff, 바뀐 부분)** — 이전과 지금의 차이만 뽑아낸 것. PR 화면의 빨간 줄(지운 것)·초록 줄(더한 것)이 그것입니다.

**리뷰 앱(PR 앱)** — 저장소에 한 번 설치해 두면 PR이 열릴 때마다 자동으로 붙어 댓글을 다는 프로그램. 내가 부르지 않아도 알아서 옵니다.

## ⚠️ 함정

**AI 리뷰를 자동 병합의 근거로 삼습니다.** 리뷰는 참고 의견이지 통과 도장이 아닙니다. 문을 지키는 건 앞 절의 검사입니다.

**AI가 «고쳐 줄까요?» 하는 대로 다 맡깁니다.** 리뷰하러 온 도구가 코드를 고치기 시작하면 리뷰가 아니라 새 작업이고, 그건 다시 리뷰받지 않은 코드입니다.

**리뷰 도구에 저장소 전체 쓰기 권한을 줍니다.** 읽기와 댓글 권한이면 충분합니다. 8절의 「에이전트 둘의 법칙」과 이어집니다.

**비공개 저장소에 앱을 붙이면서 뭘 보내는지 안 봅니다.** 코드가 밖으로 나갑니다. 개인정보가 든 코드면 한 번 더 생각합니다.

**하루 묵히기를 안 합니다.** 둘 중에 공짜인 쪽을 먼저 버리는 것입니다. 순서가 거꾸로입니다.
