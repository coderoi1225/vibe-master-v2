앞 절에서 문을 세웠지만 문지기가 없으면 문은 그냥 통로입니다. 여기서 만드는 **파일 하나**가 PR을 열 때마다 네 가지를 보고, 하나라도 걸리면 합치기 버튼이 회색이 됩니다.

## ① 넷이 각각 무엇을 막나 본다

| 검사 | 무엇을 보나 | 없으면 벌어지는 일 |
|---|---|---|
| ① 테스트 | 정해 둔 동작이 그대로 되나 | 로그인 고치다 결제가 죽는다 |
| ② 코드 정리 검사(린트) | 문법 오류·안 쓰는 것·위험한 버릇 | 빌드가 배포 단계에서야 깨진다 |
| ③ 시크릿 스캔 | 열쇠가 코드에 섞여 들어왔나 | 열쇠가 인터넷에 영원히 남는다 |
| ④ 의존성 경보 | 남의 부품에 구멍이 났나 | 내 코드는 멀쩡한데 뚫린다 |

①②는 내가 부순 것을 잡고, ③④는 밖으로 새는 것을 잡습니다. 넷 중에 뺄 것을 고르라면 **③은 절대 못 뺍니다.** 나머지 셋은 고치면 되지만 ③은 못 되돌립니다.

열쇠를 코드에 적어 올렸다가 지워도 버전 관리는 지운 것을 기억하고, 인터넷에는 새로 올라온 저장소를 자동으로 훑는 프로그램이 돌아다닙니다. 한 번 올라간 열쇠는 지우는 게 아니라 폐기하고 새로 발급받는 것입니다. 그래서 문 앞에서 막습니다.

## ② 무료로 어디까지 되나 본다

돈 이야기가 필요한 유일한 대목입니다. 정확한 값은 부록에 있습니다.

| | 공개 저장소 | 비공개 저장소 |
|---|---|---|
| 자동 실행(검사를 돌리는 시간) | 무제한 무료 | 월 일정 시간까지 무료 — 넘으면 과금 |
| 의존성 경보 | 무료 | 무료 — 둘 다 됩니다 |
| 시크릿 스캔(깃허브 기본 제공) | 무료 | 유료 등급 |
| 코드 검사(CodeQL) | 무료 | 유료 등급 |

의존성 경보는 공개든 비공개든 공짜고 설정 한 칸이니 무조건 켭니다. 비공개 저장소면 시크릿 스캔은 **무료 대체 도구** `gitleaks`를 씁니다 — 검사 안에서 프로그램 하나를 내려받아 돌리는 방식이라 깃허브 등급과 무관합니다. 자동 실행 시간은 혼자 만드는 사람이 넘길 일이 거의 없습니다.

## ③ 검사 파일을 만든다

`.github/workflows/` 폴더에 파일 하나를 둡니다. PR을 열거나 새로 밀 때마다 부품을 설치하고, 린트·테스트·빌드·시크릿 스캔을 순서대로 돌립니다.

이 파일이 [[08-자율운영/_스테이지|Stage 8]]에서 **내가 자는 동안 스스로 도는 점검의 뼈대**가 됩니다. 같은 폴더, 같은 문법이고 Stage 8에서는 «언제 도나»만 바꿔서 붙입니다. 여기서 안 만들면 Stage 8에서 처음부터 만듭니다.

## ④ 통과 필수로 건다

검사를 만들어 놓고 «필수»로 안 걸면 검사는 도는데 빨간불이어도 병합이 됩니다. 앞 절의 «Require status checks» 목록에 이 검사의 이름을 **직접 추가**해야 하고, 검사가 한 번은 돌아야 목록에 이름이 뜹니다.

## ⑤ 일부러 떨어뜨려 본다

검사는 통과하는 것을 봐서는 잘 만들었는지 모릅니다. 아무것도 안 하는 검사도 항상 통과하기 때문에, **일부러 틀려 보고 잡히는지**를 봐야 압니다.

## ⚡ 따라 하기

1. 저장소에 이 파일 하나를 만드세요 — 이게 이 절의 전부입니다. 올리면 Actions 탭에 「문지기」가 나타납니다.

```yaml
# .github/workflows/문지기.yml
name: 문지기
on:
  pull_request:            # PR을 열거나 새로 밀 때마다
  push:
    branches: [main]       # 본줄기가 바뀔 때도 한 번
  workflow_dispatch:       # 버튼으로 지금 당장 돌려보기

jobs:
  verify:                  # 아이디는 영문·숫자·- ·_ 만 (아래 기록 참고)
    name: 검사              # 화면에 보이는 이름은 한글로 써도 된다
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0            # 시크릿 스캔이 지난 기록까지 보려면 필요

      - uses: actions/setup-node@v4
        with:
          node-version-file: .nvmrc  # 판 번호는 파일에 두고 여기 안 적는다
          cache: npm

      - name: 부품 설치
        run: npm ci

      - name: ② 코드 정리 검사
        run: npm run lint

      - name: ① 테스트
        run: npm test

      - name: 굽기 — 여기서 깨지면 배포도 깨진다
        run: npm run build

      - name: ③ 시크릿 스캔
        uses: gitleaks/gitleaks-action@v2
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

### 이렇게 해 봤습니다 — 2026-09-09

이 커리큘럼 저장소에 검사 파일을 실제로 넣고 돌렸습니다. 네 가지를 봅니다 — 발행이 되나 / 절마다 필수 칸이 있나 / 코드블록 짝이 맞나 / 비밀값이 섞이지 않았나. **첫 번째는 0초 만에 실패했는데 로그가 하나도 없었습니다.** 원인은 작업 이름에 한글을 쓴 것이었습니다.

```yaml
jobs:
  검사:              # ❌ 이렇게 쓰면 파일 자체를 못 읽습니다
```
```yaml
jobs:
  verify:            # ✅ 아이디는 영문·숫자·- ·_ 만
    name: 검사        # 화면에 보이는 이름은 한글로 써도 됩니다
```

0초 만에 실패 + 로그 없음 = 거의 항상 «검사 파일 자체를 못 읽었다»는 뜻입니다. 코드가 틀린 게 아니라 설정 파일이 틀린 것이니 로그를 찾지 말고 파일부터 보세요. 고치니 7초 만에 통과했습니다.

그리고 진짜 확인은 그다음입니다. 원고 하나에서 코드블록을 안 닫고 올렸더니 「코드블록 짝이 맞나」에서 정확히 걸려 실패했고, 되돌리니 다시 통과했습니다.

2. 시크릿 스캔의 예외를 적어 두세요 — 견본 파일의 빈 값이 가짜로 걸리지 않게 하기 위해서입니다. 이 파일이 있으면 `.env.example`이 걸리지 않습니다.

```toml
# .gitleaks.toml
[allowlist]
description = "견본과 문서의 예시는 진짜 열쇠가 아니다"
paths = [
  '''\.env\.example$''',
  '''^원고/''',
  '''^docs/''',
]
```

3. 의존성 경보를 켜세요 — 설정 한 칸에 파일 한 장이고, 켜 두면 남의 부품에 구멍이 나면 고친 판으로 올리는 PR이 알아서 올라옵니다. Security 탭에 목록이 생기면 켜진 것입니다.

```
GitHub 저장소 → Settings → Advanced Security(또는 Code security)
  ☑ Dependency graph
  ☑ Dependabot alerts          ← 구멍이 나면 알려 준다
  ☑ Dependabot security updates ← 고친 판으로 올리는 PR을 대신 만들어 준다
```

```yaml
# .github/dependabot.yml — 알림이 쏟아지지 않게 주 1회로 묶는다
version: 2
updates:
  - package-ecosystem: npm
    directory: "/"
    schedule:
      interval: weekly
    open-pull-requests-limit: 3
    groups:
      묶음:
        patterns: ["*"]
```

4. 이 검사를 «통과 필수» 목록에 넣으세요 — 안 하면 앞의 셋이 다 헛것입니다. 넣고 나면 PR 화면 아래에 검사 이름이 「Required」 표시와 함께 뜹니다.

```
① 아무 가지에서 PR을 한 번 연다 → 검사가 한 번 돈다 (이름이 등록된다)
② Settings → Branches → main 규칙 편집
③ Require status checks to pass  안의 검색칸에 "검사" 를 넣어 고른다
④ Do not allow bypassing the above settings 가 켜져 있는지 다시 확인
```

5. 일부러 가짜 열쇠를 넣어 PR을 열어 보세요 — 검사가 잡는지 보기 위해서입니다. PR 화면이 빨간 X가 되고 병합 버튼이 회색이면 성공이고, 그다음 시험 가지를 치웁니다.

```bash
git switch -c 검사시험
# 가짜 열쇠를 일부러 코드에 적는다
# 진짜 열쇠 모양을 그대로 쓰면 깃허브가 «올리기 전에» 막습니다(아래 참고).
# 그래서 앞부분만 쓰고 뒤는 아무 글자나 채웁니다.
echo 'const key = "sk_live_" + "이건가짜입니다";' > 시험.js
git add 시험.js && git commit -m "일부러 열쇠를 흘려 봄"
git push -u origin 검사시험
gh pr create --fill
```

```bash
git push origin --delete 검사시험
```

### 이렇게 해 봤습니다 — push 자체가 막혔습니다

위 예시에 진짜 열쇠 모양의 글자를 적어 뒀더니, 이 교재를 공개 저장소에 올리는 순간 **깃허브가 push 자체를 막았습니다.** *"Push cannot contain secrets — Stripe API Key"* 라며 파일과 줄 번호까지 짚어 줬습니다. 가짜인데도 모양만 맞으면 걸립니다.

이건 검사보다 한 단계 앞입니다. 검사는 올라간 다음에 도는데 이건 올라가기 전에 막고, 공개 저장소에서 자동으로 켜집니다. 그래서 열쇠 예시를 적을 때는 모양을 일부러 깨뜨려 씁니다.

> **2026-09-10 확인** — **시크릿 스캔은 공개 저장소에서 자동으로 켜지고 무료**입니다.
> 비공개 저장소는 유료(Team 이상)라, 무료로 쓰려면 `gitleaks` 같은 별도 도구를 검사에 넣습니다.
> **의존성 경보는 공개·비공개 모두 무료**입니다.

## ✅ 확인

- [ ] PR을 열면 검사가 자동으로 도나 — PR 화면 아래에 검사 이름이 뜨나
- [ ] 일부러 열쇠를 넣었을 때 빨간 X가 뜨고 병합 버튼이 회색인 것을 눈으로 봤나
- [ ] 관리자인 나에게도 그 회색이 유지되나 — «관리자 권한으로 병합» 우회 버튼이 안 보이나
- [ ] 의존성 경보가 켜져 있나 — Security 탭에 목록이 나오나

둘째와 셋째가 이 장 전체의 자가 체크 첫 줄입니다.

## 📘 말 풀이

**CI(Continuous Integration, 지속적 통합)** — 합치기 전에 자동으로 검사를 돌리는 습관과 그 장치. «코드를 올리면 기계가 먼저 봐 준다»가 전부입니다.

**린트(lint)** — 코드를 읽어만 보고 문제를 찾아 주는 검사. 오타·안 쓰는 값·위험한 습관을 잡고, 옷의 보풀(lint)을 떼는 데서 온 말입니다.

**의존성 경보(Dependabot)** — 내 코드가 갖다 쓰는 남의 부품에 보안 구멍이 발견되면 알려 주고, 고친 판으로 올리는 PR을 대신 만들어 주는 기능.

## ⚠️ 함정

**검사를 만들어 놓고 «필수»로 안 겁니다.** 검사는 도는데 빨간불이어도 병합이 됩니다. ④를 다시 봅니다.

**처음부터 검사를 여덟 개 겁니다.** 매번 빨간불이 나고, 빨간불에 익숙해지면 무시하게 됩니다. 넷으로 시작합니다.

**테스트가 하나도 없는데 테스트 검사를 겁니다.** 통과는 하는데 아무것도 안 봅니다. 핵심 흐름 서너 개만 있으면 충분합니다(6절과 [[08-자율운영/_스테이지|Stage 8]]에서 이어집니다).

**의존성 PR이 매일 열 개씩 옵니다.** 처음엔 밀린 게 한꺼번에 옵니다. 보안 경보만 받게 범위를 좁히고 나머지는 주 1회로 묶습니다.

**시크릿 스캔이 가짜로 걸립니다.** 견본 파일의 빈 값이나 문서의 예시가 걸립니다. 그냥 끄지 말고 그 파일만 예외로 적습니다.

**검사가 5분 넘게 걸립니다.** 기다리기 싫어서 건너뛰게 됩니다. 오래 걸리는 것은 PR이 아니라 [[08-자율운영/_스테이지|Stage 8]]의 예약 실행으로 옮깁니다.
