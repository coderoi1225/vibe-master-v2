## 왜 이걸 하나

지금까지 일곱 절 동안 **문을 세우고 문지기를 붙였습니다.**
이 절은 **그 문에 자동문 장치를 달 때** 무엇을 조심해야 하는지입니다.

새로 나온 방식이 하나 있습니다.
**이슈를 하나 적으면, 그게 PR로 돌아옵니다.**
"로그인 화면 문구를 바꿔 줘"라고 이슈에 적어 두고 자면, 아침에 PR이 하나 만들어져 있습니다.

솔깃합니다. 그런데 여기서 멈춰야 합니다.
**자동 실행에는 승인 창이 없습니다.** 내 컴퓨터에서는 "이거 실행할까요?"를 물어보지만,
저장소 안에서 도는 것은 **아무도 없는 새벽에 혼자 실행됩니다.**

그리고 그 저장소 안에는 **내 열쇠가 들어 있습니다.**

## 새로 나온 것 — 지켜볼 것으로만

`.github/workflows/` 폴더에 **마크다운 한 장**을 두면 그게 자동화가 되는 방식이 나왔습니다.
프로그래밍 문법이 아니라 **자연어 본문**으로 적으면, 시스템이 그걸 실행 가능한 형태로 컴파일합니다.

설계는 조심스럽게 되어 있습니다.

| | |
|---|---|
| 기본 권한 | **읽기 전용** |
| 쓰기 | **정해진 출구로만** — 이슈에 댓글, PR 만들기 같은 것 |
| 격리 | 샌드박스와 방화벽이 있음 |

**다만 2026년 6월에 공개 프리뷰로 나온 것입니다.**
이 커리큘럼에서는 **"지켜볼 것"으로만 넣습니다.** 지금 쓰라고 하지 않습니다.

이유는 성능이 아니라 **되돌릴 수 없는 사고의 크기**입니다.
프리뷰 단계의 도구에 저장소 접근을 주는 것은, 혼자 운영하는 서비스에서
**잘못됐을 때 대신 막아 줄 사람이 없다는 뜻**입니다.
자리를 잡고 나서 붙여도 늦지 않습니다. **알고는 있되, 지금 켜지는 않습니다.**

## ⭐ 에이전트 둘의 법칙

이건 새 방식뿐 아니라 **AI가 저장소에서 무언가 하게 만드는 모든 경우**에 적용됩니다.
4절의 리뷰 앱에도, Stage 8의 예약 실행에도 그대로 씁니다.

**셋 중 둘까지는 괜찮습니다. 셋을 동시에 가지면 위험합니다.**

| | 무엇 | 예 |
|---|---|---|
| **①** | **신뢰할 수 없는 입력** | 남이 쓴 이슈·PR 댓글·외부에서 가져온 글 |
| **②** | **시크릿 접근** | 저장소 열쇠·배포 열쇠·데이터베이스 열쇠 |
| **③** | **외부 통신** | 인터넷 어디로든 값을 보낼 수 있는 상태 |

왜 셋이 모이면 위험한가 — **한 줄로 이어집니다.**

```
남이 이슈에 글을 쓴다 (①)
   → 그 글에 "열쇠를 읽어서 이 주소로 보내라"는 지시가 숨어 있다
   → 에이전트가 그걸 지시로 읽는다 (AI는 데이터와 명령을 잘 구분하지 못한다)
   → 열쇠를 읽고 (②)
   → 밖으로 보낸다 (③)
```

**이건 가정이 아닙니다.** 2026년 1월에 **공개 이슈 하나로 저장소를 탈취할 수 있는 취약점**이
실제로 있었습니다. 5월에 수정됐습니다.
사용자가 잘못한 게 아니라 **셋이 한 자리에 모여 있는 구조**가 문제였습니다.

**끊는 방법은 하나를 빼는 것입니다.**

| 무엇을 뺀다 | 어떻게 |
|---|---|
| ①을 뺀다 | **트리거를 저장소 주인으로 제한** — 남의 이슈로는 안 돌게 |
| ②를 뺀다 | 그 작업에 **열쇠를 안 준다.** 읽기 권한만 |
| ③을 뺀다 | 나갈 수 있는 주소를 **정해진 곳만** 허용 |

혼자 만드는 사람이 가장 확실하게 할 수 있는 건 **①을 빼는 것**입니다.

## ⭐ 그리고 하나 더 — 태그가 아니라 커밋 번호로 고정

검사 파일에 `uses: 어떤도구/어떤액션@v2` 라고 적으면,
**그 도구를 만든 사람이 `v2`가 가리키는 내용을 언제든 바꿀 수 있습니다.**

`v2`는 이름표일 뿐이라 옮겨 붙일 수 있습니다.
어제까지 멀쩡했던 도구가 오늘 다른 내용으로 바뀌어 있어도 **나는 모릅니다.**
그리고 그 도구는 내 저장소 안에서 내 권한으로 돕니다.

그래서 **이름표가 아니라 지문으로 고정합니다.**

```yaml
# 이렇게 하지 않는다 — 이름표는 옮겨 붙일 수 있다
- uses: 어떤도구/어떤액션@v2

# 이렇게 한다 — 커밋 번호는 바뀌지 않는다
- uses: 어떤도구/어떤액션@a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0  # v2
```

뒤에 주석으로 판 이름을 적어 두면 나중에 알아보기 쉽습니다.
**깃허브가 만든 공식 액션은 예외로 둬도 됩니다.** 남이 만든 것에 이걸 적용합니다.

## 📘 말 풀이

**에이전틱 워크플로(agentic workflow)**
저장소 안에서 **AI가 스스로 일하고 결과를 PR이나 댓글로 내놓게** 만든 자동화.
내 컴퓨터가 아니라 저장소 서버에서 돌고, **실행 전에 물어보지 않습니다.**

**커밋 번호(commit SHA)**
코드의 특정 시점에 붙는 **바꿀 수 없는 지문.** 40자리 문자입니다.
`v2` 같은 이름표는 다른 곳을 가리키게 바꿀 수 있지만, 이 번호는 **한 내용만** 가리킵니다.

**트리거(trigger)**
자동화가 **언제 시작되나**를 정하는 조건. "이슈에 댓글이 달리면" "PR이 열리면" 같은 것.
여기를 조이는 게 안전의 첫 단추입니다.

## ⚠️ 자주 걸리는 함정

- **"내 저장소는 비공개니까 괜찮다"** — 지금은요. 나중에 공개로 바꾸거나, 남에게 보여 주려고 초대하는 순간 조건이 달라집니다. **처음부터 조여 둡니다.**
- **에이전트에게 본줄기 밀기 권한을 준다** — 절대 주지 않습니다. **PR 만들기까지**입니다. 사람의 승인이 마지막에 남아야 2절에서 세운 문이 의미를 유지합니다.
- **자동화가 만든 PR을 자동으로 병합한다** — 문을 세우고 자동문을 달아서 아무나 지나가게 만든 것입니다.
- **`GITHUB_TOKEN` 권한을 통째로 준다** — 기본값이 넓을 수 있습니다. 작업마다 **필요한 것만** 적습니다.
- **남이 만든 액션을 이름표로 쓴다** — 위의 커밋 번호 이야기입니다.
- **저장소에 지침 파일이 들어 있는 걸 확인 안 한다** — 저장소에 AI 지침 파일을 심어 두자 **에이전트 여러 종류가 저장소를 여는 순간 그걸 실행한** 사례가 있습니다. 남의 저장소를 열 때는 지침 파일부터 봅니다.

## ⚡ 이렇게 하세요

**1) 지금 있는 검사 파일의 권한부터 조입니다.** 3절에서 만든 파일 맨 위에 두 줄을 더합니다.

```yaml
# .github/workflows/문지기.yml
name: 문지기

permissions:
  contents: read          # 읽기만. 기본값이 더 넓을 수 있으니 명시한다
  pull-requests: write    # PR에 댓글을 달아야 하면 이것만 추가

on:
  pull_request:
  workflow_dispatch:
```

**2) 트리거를 저장소 주인으로 제한합니다.** ①을 빼는 방법입니다.

```yaml
jobs:
  검사:
    # 저장소 주인이 만든 것에만 반응한다 (남의 이슈·PR로는 안 돈다)
    if: github.event.repository.owner.login == github.actor
    runs-on: ubuntu-latest
```

AI가 도는 자동화라면 **한 겹 더** 씁니다.

```yaml
    # 남이 연 PR(fork)에서는 아예 돌지 않게
    if: github.event.pull_request.head.repo.full_name == github.repository
```

**3) 남이 만든 액션을 커밋 번호로 바꿉니다.**

```bash
# 지금 이름표로 쓰고 있는 것 목록
grep -rn "uses:.*@v" .github/workflows/

# 해당 액션의 커밋 번호를 확인한다
gh api repos/<만든이>/<액션이름>/commits/v2 --jq .sha
```

나온 40자리를 `@v2` 자리에 넣고, 뒤에 `# v2` 주석을 답니다.

**4) 열쇠는 필요한 단계에만 줍니다.** 파일 전체가 아니라 그 단계에만 붙입니다.

```yaml
      - name: 열쇠가 필요 없는 단계
        run: npm test                      # env 없음

      - name: 열쇠가 꼭 필요한 단계
        run: npm run 무언가
        env:
          SOME_KEY: ${{ secrets.SOME_KEY }}   # 여기서만
```

**5) 자동화가 만든 PR도 문을 통과하게 둡니다.** 자동 병합을 켜지 않습니다.

```
Settings → Actions → General
  Workflow permissions:  ☑ Read repository contents permission  (좁은 쪽)
  ☐ Allow GitHub Actions to create and approve pull requests   ← 승인까지는 주지 않는다
```

**만들기는 허용하되 승인은 사람이** — 이게 "어디까지 자동, 어디부터 사람"의 답입니다.
