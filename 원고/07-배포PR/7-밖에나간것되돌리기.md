Stage 4.5에서 되돌리기를 배웠습니다. 그건 **내 컴퓨터 안**이었습니다.
망쳐도 나만 봤습니다.

**여기는 밖입니다.** 지금 사이트가 이상하면 **그동안 들어온 사람들이 그걸 봅니다.**
그래서 계산이 달라집니다. 내 컴퓨터에서는 "원인을 찾고 고치는" 게 맞지만,
밖에서는 **먼저 되돌리고 원인은 나중에 찾는** 게 맞습니다.

그리고 이 절이 이 장에서 **가장 많이 건너뛰는 절**입니다.
"되돌리는 버튼이 있다더라"까지만 읽고 넘어갑니다.
그러다 진짜 급할 때 **처음 해 봅니다.** 그때는 손이 떨리고 화면이 낯섭니다.

**연습하는 데 5분이고, 안 해서 잃는 건 한 시간입니다.**

## ① 되돌리는 길은 셋입니다 — 빠른 순서로

| 길 | 걸리는 시간 | 언제 |
|---|---|---|
| **① 스위치를 끈다** | **몇 초** | 새 기능 하나가 문제일 때 (5절) |
| **② 이전 배포로 되돌린다** | **1분 안팎** | 배포 전체가 이상할 때. **가장 자주 쓰는 길** |
| **③ 되돌리는 커밋을 만든다** | 몇 분 | ②로 급한 불을 끈 뒤, 저장소를 정리할 때 |

**순서가 중요합니다.** 급할 때는 ①→②이고, ③은 그다음입니다.
③부터 시작하면 다시 굽고 배포하는 시간만큼 사고가 길어집니다.

### ②가 왜 그렇게 빠른가

배포 서비스는 배포할 때마다 **구운 결과물을 통째로 따로 보관합니다.**
새 판이 나와도 옛 판이 지워지는 게 아니라, **주소가 가리키는 곳만 바뀝니다.**

```
   내 주소  ──────▶  [ 3번째로 구운 것 ]   ← 지금
                     [ 2번째로 구운 것 ]   ← 아직 남아 있다
                     [ 1번째로 구운 것 ]   ← 이것도
```

그래서 되돌리는 건 **다시 굽는 게 아니라 화살표를 옮기는 것**입니다.
버튼 한 번이고, 코드는 손대지 않습니다.

### ②만으로는 끝나지 않는 이유

②로 화면은 돌아왔습니다. 그런데 **저장소의 본줄기에는 문제의 코드가 그대로 있습니다.**
그 상태에서 다음에 무언가를 병합하면 **문제의 코드가 다시 나갑니다.**

그래서 ②로 불을 끈 다음, 반드시 ③으로 저장소를 맞춰 놓습니다.
③은 지우는 게 아니라 **"되돌린다"는 새 기록을 하나 더 얹는 것**입니다.
이미 밖에 나간 기록은 지우지 않습니다.

## ⚠️ 되돌려도 안 돌아오는 것

이게 이 절에서 가장 중요한 대목입니다. **되돌리기가 만능이 아닙니다.**

| 되돌아온다 | 안 돌아온다 |
|---|---|
| 화면·기능·코드 | **데이터베이스 구조를 바꾼 것** |
| 설정값 | **보낸 메일·알림** |
| 스위치 상태 | **처리된 결제** |
| | **사용자가 지운 것** |

코드는 화살표를 옮기면 되지만, **데이터는 시간이 한 방향으로만 흐릅니다.**

특히 데이터베이스에서 **칸을 하나 지우는 변경**은 되돌릴 수 없습니다.
코드를 옛 판으로 돌려놨는데 그 코드가 찾는 칸이 이미 사라져 있으면, 사이트는 그대로 죽어 있습니다.

> **그래서 규칙 하나** — 데이터베이스에서 **지우는 변경은 코드 변경과 같은 PR에 넣지 않습니다.**
> 먼저 "새 칸을 더하는" 변경만 내보내고, 코드가 새 칸을 쓰기 시작한 뒤,
> **한참 지나서** 옛 칸을 지우는 PR을 따로 냅니다.

## 📘 말 풀이

**롤백(rollback, 되돌리기)**
지금 밖에 나가 있는 것을 **바로 전의 멀쩡했던 상태로 되돌리는 일.**
코드를 고치는 게 아니라, 주소가 가리키는 곳을 옛 판으로 바꾸는 것입니다.

**리버트(revert, 되돌리는 커밋)**
이미 합쳐진 변경을 **취소하는 새 커밋을 하나 더 만드는 것.**
지우는 게 아니라 "이걸 물린다"고 기록으로 남깁니다. 밖에 나간 기록은 지우지 않습니다.

**마이그레이션(migration, 데이터 구조 변경)**
데이터베이스의 **모양을 바꾸는 일**(칸을 더하거나 지우거나).
코드와 달리 **되돌리기가 어렵거나 불가능**합니다. 그래서 따로 다룹니다.

## ⚠️ 함정

- **급한데 원인부터 찾는다** — 사고 중에 원인 분석은 사치입니다. **먼저 되돌리고, 그다음에 찬찬히 봅니다.**
- **급하다고 브랜치 보호를 끈다** — 2절에서 세운 문을 사고 중에 부수는 겁니다. 규칙은 그대로 두고 되돌립니다.
- **되돌리고 저장소를 안 맞춘다** — 화면은 돌아왔는데 본줄기에 문제 코드가 남아 있어서, 다음 배포에 **똑같은 사고가 다시 납니다.**
- **밖에 나간 기록을 지우려 한다**(`push --force`) — 되돌리기가 아니라 역사 조작입니다. 협업자가 없어도 하지 않습니다. `revert`를 씁니다.
- **데이터 구조 변경을 코드와 같이 내보낸다** — 되돌릴 수 없는 상태가 만들어지는 거의 유일한 경로입니다.
- **연습을 안 한다** — 이 절 전체의 함정입니다. 읽었다고 되는 게 아닙니다.

## ⚡ 따라 하기

**1) 지금 당장, 안 급할 때 되돌리는 연습을 합니다.** 이게 이 절의 전부입니다.

```
① 아무 티 안 나는 변경을 하나 내보낸다 (예: 화면 아래 문구 한 글자)
② 실서비스 주소를 열어 바뀐 것을 눈으로 확인한다
③ 배포 서비스 → Deployments → 바로 이전 배포 → ⋯ → Promote to Production
   (또는 Instant Rollback / Rollback 이라는 이름)
④ 실서비스 주소를 새로고침 — 원래 문구로 돌아왔나
⑤ ③을 누른 순간부터 ④까지 몇 초 걸렸는지 센다
```

**⑤에서 잰 시간이 앞으로 사고가 났을 때의 복구 시간입니다.** 그 숫자를 알아 두는 게 목적입니다.

**2) 터미널로도 할 수 있게 명령을 적어 둡니다.** 휴대폰만 있을 때를 대비해 화면 방법도 같이 압니다.

```bash
# 지금까지의 배포 목록 — 맨 위가 지금 나가 있는 것
vercel ls

# 바로 이전 것으로 되돌리기
vercel rollback <이전_배포_주소>
```

**3) 불을 끈 다음, 저장소를 맞춥니다.**

```bash
# 어떤 병합이 문제였는지 찾는다
git log --oneline -10

# 그 병합을 되돌리는 새 커밋을 만든다
git switch -c 되돌리기-0909
git revert -m 1 <문제의_커밋번호>     # 병합 커밋이면 -m 1 이 필요하다
git push -u origin 되돌리기-0909
gh pr create --title "되돌리기 — 0909 취합" --body "사고 대응. 원인 분석은 별도 이슈."
```

**되돌리는 PR도 문을 통과시킵니다.** 급하다고 규칙을 끄지 않습니다.
검사는 몇 분이고, 이미 ②로 화면은 돌아와 있습니다.

**4) 3줄 부검을 남깁니다.** 비난할 사람이 없어도 씁니다. 목적은 처벌이 아니라 재발 방지입니다.

```markdown
<!-- docs/사고/2026-09-09.md -->
## ② 무슨 일이
결제 실패 시 화면에 "성공"이 떴다. 07:40~08:05 (25분)

## ③ 왜 막지 못했나
결제 실패 경로에 테스트가 없었다. 검사는 초록불이었다.

## ④ 다음에 안 나게 하려면
결제 실패 흐름을 테스트에 추가한다 → #12
```

**5) 되돌릴 수 없는 것의 목록을 만들어 둡니다.** 내 서비스에서 무엇이 그런지 적어 둡니다.

```markdown
<!-- docs/되돌릴수없는것.md -->
- 결제 승인 (취소는 되지만 되돌리기는 아님)
- 사용자에게 나간 메일·알림
- 데이터베이스에서 칸을 지우는 변경
- 사용자가 지운 글
```

- [ ] 되돌리는 데 **몇 초 걸렸는지 아나**
