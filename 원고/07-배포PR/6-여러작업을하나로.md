AI에게 일을 시키는 방식이 바뀌었습니다.
예전에는 하나 시키고 기다렸습니다. 지금은 **세 개를 동시에 시켜 놓고 다른 일을 합니다.**

그러면 30분 뒤 이런 상태가 됩니다.

```
가지 A — 로그인 화면 문구 고침       (끝남)
가지 B — 결제 실패 처리 추가         (끝남)
가지 C — 목록 화면 정렬 바꿈         (끝남)
```

여기서 대부분이 실수합니다. **셋을 각각 병합해 버립니다.** 빠르니까요.
그리고 저녁에 사이트가 이상해집니다. **셋 중 무엇 때문인지 모릅니다.**
하나를 되돌리면 나머지 둘의 작업이 그 위에 얹혀 있어서 같이 뽑힙니다.

실제로 여러 개를 돌려 본 사람이 남긴 말이 이겁니다 —
*"에이전트를 많이 돌릴수록 병목은 결국 나라는 게 뼈저리게 느껴진다."*
만드는 속도는 늘었는데 **보는 속도는 그대로**입니다.
이 절은 **보는 자리를 한 곳으로 모으는 방법**입니다.

## ① 마무리 흐름 넷

```
① 취합    — 흩어진 가지를 모으는 가지 하나로 합친다
② PR 하나 — 그 가지에서 PR을 딱 한 건 연다
③ 리뷰    — 만들기 전에 다른 AI에게 전체를 한 번 보인다
④ 생성    — 그제야 본줄기로 병합한다
```

**③이 ④보다 앞에 있는 게 핵심입니다.**
합쳐 놓고 나서 리뷰하는 게 아니라, **합치기 전에** 봅니다.
합친 뒤에 발견하면 되돌리기가 시작되고, 그 순간부터 일이 커집니다.

### 왜 PR을 하나로 모으나 — 세 가지

| 이유 | 흩어 올렸을 때 | 하나로 모았을 때 |
|---|---|---|
| **되돌리기** | 세 번 되돌려야 하고 순서가 꼬인다 | **한 번에 물린다** |
| **충돌 발견** | 병합할 때마다 하나씩 터진다 | 취합 가지에서 **한 번에 본다** |
| **리뷰** | 세 번 읽고 셋의 관계는 아무도 안 본다 | **셋이 서로를 부수는지**가 보인다 |

세 번째가 특히 큽니다.
A는 맞고 B도 맞는데, **A와 B가 같이 있으면 틀린 경우**가 있습니다.
각각 보면 절대 안 보입니다. 한 화면에 놓아야 보입니다.

## ② 언제 하나로 묶고, 언제 따로 두나

무조건 묶는 게 아닙니다. 기준은 **"같이 되돌려도 괜찮은가"**입니다.

| | |
|---|---|
| **묶는다** | 같은 화면·같은 기능을 건드린 것 / 셋 다 오늘 만든 것 / 서로 얽혀 있는 것 |
| **따로 둔다** | 급한 사고 수정 — **혼자 먼저 나가야 되돌리기가 쉽다** / 성격이 완전히 다른 것 / 하나가 유독 큰 것 |

**급한 수정은 절대 묶지 않습니다.** 묶는 순간 그 수정도 다른 것들과 운명을 같이합니다.

## 📘 말 풀이

**취합 가지(integration branch)**
여러 가지를 **일단 모아 보는 임시 가지.** 본줄기가 아니라서 여기서 깨져도 사용자는 모릅니다.
모아 보고 괜찮으면 본줄기로 보내고, 아니면 이 가지를 버립니다.

**충돌(conflict)**
두 가지가 **같은 파일의 같은 줄**을 서로 다르게 고쳤을 때, 컴퓨터가 어느 쪽이 맞는지 몰라서
사람에게 물어보는 상태. 오류가 아니라 질문입니다.

## ⚠️ 함정

- **끝난 순서대로 그냥 병합한다** — 가장 흔합니다. 빠르지만 되돌릴 수 없는 상태가 됩니다.
- **충돌이 나면 겁먹고 처음부터 다시 시킨다** — 충돌은 오류가 아니라 질문입니다. **양쪽 코드를 다 보여 주고** AI에게 어느 쪽이 맞는지 판단시킵니다.
- **AI에게 충돌 해결을 맡기고 결과를 안 본다** — 한쪽을 통째로 버리는 방식으로 "해결"하는 경우가 있습니다. 충돌 해결은 **되돌리기 어려운 축**에 듭니다. 반드시 눈으로 봅니다.
- **취합 가지에서 검사를 안 돌린다** — 각각의 가지는 초록불이었는데 **합치면 빨간불**인 경우가 정확히 이 절이 노리는 것입니다. 취합 가지에서 반드시 한 번 더 돌립니다.
- **묶은 PR이 너무 커진다** — 파일 서른 개짜리 PR은 아무도 안 읽습니다(나 자신 포함). **500줄이 넘으면 둘로 쪼갭니다.**
- **급한 사고 수정을 같이 묶는다** — 사고 수정은 혼자 먼저 보냅니다.

## ⚡ 따라 하기

**1) 취합 가지를 하나 만듭니다.** 본줄기의 최신 상태에서 시작합니다.

```bash
git switch main
git pull
git switch -c 취합-0909        # 날짜를 붙이면 나중에 찾기 쉽다
```

**2) 끝난 가지들을 하나씩 끌어옵니다.** 한 번에 셋을 하지 않습니다.

```bash
git merge origin/기능-로그인문구
git merge origin/기능-결제실패
git merge origin/기능-목록정렬
```

충돌이 나면 거기서 멈춥니다. 그때는 아래 프롬프트를 씁니다.

```
git merge 중에 충돌이 났다. 아래는 충돌 표시가 들어간 파일 내용이다.
나는 비개발자다. 다음을 알려줘.

① 두 쪽이 각각 무엇을 하려던 코드인가 (한 줄씩, 쉬운 말로)
② 둘 다 살릴 수 있나, 아니면 하나를 버려야 하나
③ 버려야 한다면 무엇을 잃게 되나
④ 최종본 전체를 붙여 줘 (충돌 표시 없이)

(여기에 충돌 난 파일 내용을 그대로 붙여넣기)
```

**3) 검사를 한 번 돌립니다.** 합쳐진 상태에서 초록불인지 봅니다.

```bash
npm run lint && npm test && npm run build
```

여기서 깨지면 **셋을 각각 병합했을 때 발견 못 했을 것**입니다. 이게 이 절의 값입니다.

**4) PR을 딱 하나 엽니다.**

```bash
git push -u origin 취합-0909
gh pr create --title "0909 취합 — 로그인 문구·결제 실패 처리·목록 정렬" --body-file - <<'PR'
## ③ 무엇을
가지 셋을 하나로 모았습니다.
- 기능-로그인문구
- 기능-결제실패
- 기능-목록정렬

## ④ 왜
각각 병합하면 되돌릴 때 순서가 꼬입니다. 한 번에 물릴 수 있게 묶습니다.

## ⑤ 어떻게 확인했나
- [ ] 취합한 상태에서 검사 초록불
- [ ] 미리보기 주소에서 세 화면을 직접 눌러 봄

## ⑥ 되돌리는 법
이 PR 하나를 되돌리면 셋이 함께 사라집니다.
PR
```

**5) ⭐ 병합 버튼을 누르기 전에** 다른 AI에게 전체를 한 번 보입니다.

```bash
git diff origin/main...HEAD > /tmp/취합.diff
```

```
아래는 서로 다른 작업 셋을 하나로 합친 변경(diff)이다.
각각은 따로 보면 문제가 없다고 가정하고, 다음 하나만 봐 줘.

★ 이 셋이 함께 있을 때만 생기는 문제가 있나?
  - 같은 값을 두 곳에서 다르게 바꾸지 않았나
  - 한쪽이 지운 것을 다른 쪽이 쓰고 있지 않나
  - 화면 흐름이 서로 어긋나지 않나

있으면 파일:줄번호와 함께, 없으면 "없음"이라고만 답해라.

(여기에 취합.diff 를 붙여넣기)
```

**6) 그다음 병합합니다.** 그리고 다 쓴 가지들을 치웁니다.

```bash
gh pr merge --squash --delete-branch
git push origin --delete 기능-로그인문구 기능-결제실패 기능-목록정렬
```

`--squash`는 **셋의 커밋을 하나로 눌러서** 본줄기에 넣는 것입니다.
그러면 나중에 되돌릴 때 **그 한 개만 물리면 됩니다.**

## ✅ 확인

- [ ] 가지 둘 이상을 **취합 가지 하나로** 모아 봤나
- [ ] 합쳐진 상태에서 **검사가 초록불**인가
- [ ] 본줄기로 나간 PR이 **한 건**인가 (여러 건이 아니라)
- [ ] 병합 **전에** 다른 AI에게 전체를 보였나
- [ ] 다 쓴 가지를 **지웠나**
- [ ] 이 변경 전체를 **한 번에 되돌릴 수 있나** — 되돌릴 지점 하나를 지목할 수 있나

마지막 항목이 이 절의 목적입니다. 지목할 수 없으면 흩어 올린 것입니다.
