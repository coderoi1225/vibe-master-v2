## 왜 이걸 하나

여기가 이 장의 심장입니다.

혼자 만드는 사람이 PR을 건너뛰는 이유는 하나입니다 — **"내가 다 아는데 나한테 왜 요청해."**
맞는 말처럼 들립니다. 그런데 실제로 벌어지는 일은 이렇습니다.

밤 11시에 AI가 파일 여덟 개를 고쳤습니다. 화면에서 잘 돕니다. 바로 올립니다.
아침에 사이트가 죽어 있습니다. **여덟 개 중 무엇이 죽였는지 모릅니다.**
그리고 그때는 이미 사용자가 그 화면을 봤습니다.

PR은 **문 하나**입니다. 통과해야 들어옵니다.
그 문을 세우는 데 드는 시간은 30분이고, 없어서 잃는 시간은 하루입니다.

이 절을 건너뛰면 뒤의 절 여섯이 걸릴 자리가 없습니다.
검사도 AI 리뷰도 **전부 PR 위에 얹힙니다.**

## PR이 무엇인가 — 한 문장

**"이 가지에서 한 변경을, 본줄기에 합쳐 주세요"라는 요청서**입니다.

Stage 4.5에서 가지(브랜치)를 배웠습니다. 본줄기를 그대로 두고 옆에 갈라 놓은 작업 공간입니다.
PR은 그 옆 공간의 작업을 **본줄기로 돌려보내는 절차**입니다.

```
main (본줄기)  ────────●────────────────────●─────▶  실서비스로 나감
                        \                  /
가지                     ●──●──●──────────●
                              작업        └─ 여기서 PR을 연다
```

회사에서는 여기서 동료가 봅니다. 혼자면 볼 사람이 없습니다.
**그래서 PR이 필요 없는 게 아니라, 그래서 더 필요합니다.**
동료가 없으니 **문이라도 있어야** 합니다.

## 혼자여도 남는 실익 셋

### ① 검사를 통과 못 하면, 병합 자체가 안 됩니다

이게 첫 번째이자 가장 큰 실익입니다.

내가 방심해도 **기계는 방심하지 않습니다.**
빌드가 깨졌으면 합칠 수 없고, 테스트가 떨어졌으면 합칠 수 없고,
열쇠가 섞여 들어갔으면 합칠 수 없습니다. **버튼이 회색이 되어 안 눌립니다.**

의지로 지키는 규칙은 새벽 2시에 무너집니다. 버튼이 안 눌리는 것은 안 무너집니다.
다음 절에서 이 검사 넷을 실제로 겁니다.

### ② 바뀐 부분만, 남의 코드처럼 다시 보게 됩니다

PR 화면에는 **바뀐 줄만** 나옵니다. 빨간 줄과 초록 줄로.

만들 때는 파일을 하나씩 보지만, PR 화면은 **변경 전체를 한 장으로** 보여 줍니다.
그러면 이런 게 보입니다 — 지우려던 파일이 안 지워졌네, 연습용 코드가 딸려 왔네,
고쳐 달라고 한 적 없는 파일이 왜 바뀌었지.

**AI에게 시킬수록 이게 중요해집니다.** AI는 시키지 않은 것도 함께 고칩니다.
악의가 아니라 친절인데, 그 친절이 다른 데를 부숩니다.
PR 화면은 **그 친절이 어디까지 갔는지** 보여 주는 유일한 자리입니다.

### ③ 왜 바꿨는지가 기록으로 남습니다

3개월 뒤의 나는 남입니다. 그리고 **AI는 기억이 아예 없습니다.**

커밋 메시지는 "무엇을 바꿨나"를 남기지만, PR은 **"왜"**를 남깁니다.
그 화면에 스크린샷도, 시험해 본 경로도, 걱정되는 지점도 같이 남습니다.

나중에 "이 기능 왜 이렇게 만들었지?"를 검색하면 그 PR이 나옵니다.
그리고 그걸 **AI에게 그대로 읽힐 수 있습니다.**

## ⭐ 핵심 설정 셋 — 이것만 켜면 됩니다

PR을 열기만 하고 이 설정을 안 하면 **아무 힘이 없습니다.**
언제든 문을 안 거치고 본줄기에 바로 밀어 넣을 수 있으니까요.

저장소 설정에서 **본줄기(main)에 규칙 하나**를 겁니다.

| 무엇 | 무슨 뜻 | 왜 |
|---|---|---|
| **① 브랜치 보호** | 본줄기에 **직접 밀어 넣기 금지**. 반드시 PR을 거친다 | 문을 세운다 |
| **② 검사 통과 필수** | 걸어 둔 검사가 **초록불이 아니면 합치기 버튼이 안 눌린다** | 문을 지킨다 |
| **③ 관리자에게도 적용** | **저장소 주인인 나도 이 규칙을 지킨다** | 문이 나에게도 문이 된다 |

**③을 안 켜면 앞의 둘이 없는 것과 같습니다.**

저장소 주인은 기본적으로 규칙의 예외입니다.
검사가 빨간불이어도 "관리자 권한으로 병합" 버튼이 뜹니다. 그리고 급할 때 그걸 누릅니다.
**급할 때 누르라고 있는 버튼이 아니라, 급할 때 누르게 되는 버튼입니다.**

혼자 만드는 사람에게 이 항목 하나가 **이 장 전체의 핵심**입니다.
막을 사람이 나뿐인데, 나를 안 막으면 아무도 안 막는 겁니다.

> **정말 급하면 어떻게 하나** — 규칙을 끄지 않습니다. **되돌립니다**(7절).
> 앞으로 밀어붙이는 것보다 뒤로 물러나는 게 항상 빠릅니다.

## 📘 말 풀이

**PR(Pull Request, 풀 리퀘스트)**
**"이 가지에서 한 변경을 본줄기에 합쳐 주세요"라는 요청서.**
요청과 승인 사이에 자동 검사와 리뷰가 들어갑니다. 혼자면 내가 요청하고 내가 승인합니다.

**병합(merge, 머지)**
가지에서 한 작업을 **본줄기에 합쳐 넣는 것**. 합쳐지는 순간이 곧 실서비스로 나가는 순간입니다.
그래서 그 직전에 문을 세웁니다.

**브랜치 보호(branch protection)**
본줄기에 **아무나·아무렇게나 못 들어가게 거는 규칙**.
"PR을 거쳐라 / 검사를 통과해라 / 주인도 예외 없다" 셋을 여기서 켭니다.

## ⚠️ 자주 걸리는 함정

- **PR만 열고 보호는 안 건다** — 가장 흔합니다. 습관만 남고 강제력이 없어서, 바쁜 날 그냥 본줄기에 밀어 넣습니다.
- **관리자 예외를 안 끈다** — 이 장에서 딱 하나만 기억한다면 이겁니다. 안 끄면 규칙이 나에게만 적용되지 않고, 저장소에 나밖에 없습니다.
- **PR 하나에 열 가지를 담는다** — 뭐가 문제인지 못 찾고, 되돌리면 멀쩡한 것까지 같이 사라집니다. **한 PR = 한 가지 일.**
- **제목이 "수정"** — 3개월 뒤에 아무 도움이 안 됩니다. "무엇을 왜"를 한 줄로 씁니다.
- **자기 PR을 안 읽고 병합한다** — 실익 ②가 통째로 날아갑니다. 열었으면 **바뀐 줄은 반드시 눈으로 훑습니다.**
- **가지를 안 만들고 본줄기에서 작업한다** — 보호를 걸면 밀어 넣는 순간 거부당합니다. 거부가 정상입니다. 그때 가지를 만듭니다.

## ⚡ 이렇게 하세요

**1) 가지를 하나 만들고 작업합니다.**

```bash
git switch -c 기능-로그인화면        # 가지 하나 = 일 하나
# ... AI와 작업 ...
git add -A
git commit -m "로그인 화면 오류 문구를 한국어로 바꿈"
git push -u origin 기능-로그인화면
```

**2) PR을 엽니다.** 밀어 넣고 나면 GitHub 화면 위에 "Compare & pull request" 단추가 뜹니다.
터미널에서 바로 열 수도 있습니다.

```bash
gh pr create --fill --web
```

**3) PR 본문에 이 다섯 줄을 씁니다.** 저장소에 견본을 넣어 두면 매번 자동으로 채워집니다.

```markdown
<!-- .github/pull_request_template.md -->
## 무엇을
(한 줄)

## 왜
(한 줄 — 3개월 뒤의 나와 AI가 읽습니다)

## 어떻게 확인했나
- [ ] 미리보기 주소에서 직접 눌러 봤다
- [ ] 실패하는 경우도 해 봤다(빈칸·잘못된 값)

## 되돌리는 법
(이 변경이 사고를 내면 무엇을 되돌리면 되나)
```

**4) ⭐ 본줄기에 보호를 겁니다.** 이 절의 핵심입니다.

```
GitHub 저장소 → Settings → Branches → Add branch protection rule

  Branch name pattern:  main

  ☑ Require a pull request before merging
  ☑ Require status checks to pass before merging     ← 다음 절에서 검사를 여기에 넣습니다
  ☑ Do not allow bypassing the above settings        ← ★ 관리자인 나에게도 적용
```

마지막 항목의 이름은 화면 판에 따라 「Include administrators」로 보이기도 합니다.
**뜻은 같습니다 — 주인도 예외 없음.**

**5) 일부러 어겨 봅니다.** 이게 확인의 전부입니다.

```bash
git switch main
echo "규칙 시험" >> README.md
git add README.md && git commit -m "일부러 본줄기에 직접"
git push
```

**거부당해야 정상입니다.** `protected branch hook declined` 같은 말이 나옵니다.
그러면 방금 만든 커밋을 없애고 가지로 다시 갑니다.

```bash
git reset --hard origin/main     # 방금 만든 커밋을 지운다 (밀기 전이라 안전)
```

### 이렇게 해 봤습니다 — 2026-09-09 · ⚠️ 무료로는 문을 «잠글» 수 없습니다

이 절이 시키는 대로 실제로 해 봤습니다. **PR을 열고 검사를 걸고 병합까지는 됐습니다.**
그런데 **브랜치 보호를 켜는 데서 막혔습니다.**

> *"GitHub Pro로 올리거나, 이 저장소를 공개로 바꾸세요."*

규칙집(ruleset)이라는 다른 방식도 시도했는데 **똑같이 거절당했습니다.**

**무료 계정 + 비공개 저장소** 조합에서는 **검사 통과를 강제할 수 없습니다.**
검사는 돌고 결과도 보이지만, **떨어져도 병합 버튼이 살아 있습니다.** 문은 세웠는데 잠금장치가 없는 상태입니다.

**그래서 길이 셋입니다.**

| 길 | 무엇이 되나 | 무엇을 내주나 |
|---|---|---|
| **저장소를 공개로** (추천) | 보호·검사 강제 · 자동 실행 무제한 · 비밀값 스캔 · 코드 검사 **전부 무료** | 코드를 남이 봅니다. **비밀값을 코드에 안 두면 문제 없습니다** — 이 커리큘럼이 계속 말하는 그것입니다 |
| 유료로 올리기 | 비공개 그대로 전부 됨 | 돈 |
| 그냥 이대로 | PR 기록·검사 결과는 남음 | **강제가 안 됩니다.** 내가 규칙을 지켜야 합니다 |

앞 3절에서 «자동 실행은 공개는 무제한, 비공개는 시간 제한»이라고 했는데 **여기도 같은 갈림길입니다.**
**공개/비공개는 취향이 아니라 무엇이 무료로 되느냐를 가르는 선입니다.** 배우는 단계라면 공개로 두는 쪽이 훨씬 유리합니다.

## ✅ 됐는지 확인

- [ ] PR을 **한 건 열어 봤나**
- [ ] PR 화면에서 **빨간 줄·초록 줄로 바뀐 부분이 보이나**
- [ ] 본줄기에 **직접 밀어 넣기가 거부되나** — 실제로 해 보고 거부 메시지를 봤나
- [ ] ⭐ **검사를 통과 못 하면 합쳐지지 않게 막았나 — 나 자신에게도 적용되게 켰나**
- [ ] PR 화면 아래에 **미리보기 주소 링크**가 붙어 있나
- [ ] PR 본문에 **"왜"가 한 줄이라도 적혀 있나**

네 번째가 «아니오»면 이 절을 안 한 것과 같습니다. 다시 설정 화면으로 갑니다.
