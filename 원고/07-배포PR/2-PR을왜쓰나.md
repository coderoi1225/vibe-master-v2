여기가 이 장의 심장입니다. 밤 11시에 AI가 파일 여덟 개를 고친 것을 바로 올렸다가 아침에 사이트가 죽어 있으면 여덟 개 중 무엇이 죽였는지 모르는데, PR은 그 사이에 세우는 **문 하나**입니다.

## ① PR이 무엇인지 한 줄로 본다

«이 가지에서 한 변경을 본줄기에 합쳐 주세요»라는 **요청서**입니다. Stage 4.5에서 배운 가지(브랜치)는 본줄기를 그대로 두고 옆에 갈라 놓은 작업 공간이고, PR은 그 작업을 본줄기로 돌려보내는 절차입니다.

```
main (본줄기)  ────────●────────────────────●─────▶  실서비스로 나감
                        \                  /
가지                     ●──●──●──────────●
                              작업        └─ 여기서 PR을 연다
```

회사에서는 여기서 동료가 봅니다. 혼자면 볼 사람이 없는데, 그래서 PR이 필요 없는 게 아니라 그래서 더 필요합니다. 동료가 없으니 문이라도 있어야 합니다.

## ② 혼자여도 남는 실익 셋을 본다

첫째, 검사를 통과 못 하면 병합 자체가 안 됩니다. 빌드가 깨졌거나 열쇠가 섞여 들어갔으면 **버튼이 회색이 되어 안 눌립니다.** 의지로 지키는 규칙은 새벽 2시에 무너지지만 버튼이 안 눌리는 것은 안 무너집니다.

둘째, 바뀐 부분만 남의 코드처럼 다시 보게 됩니다. PR 화면은 변경 전체를 빨간 줄·초록 줄 한 장으로 보여 주어서, 지우려던 파일이 안 지워진 것과 시키지 않은 파일이 바뀐 것이 보입니다. AI는 시키지 않은 것도 함께 고치는데, PR 화면은 그 친절이 어디까지 갔는지 보여 주는 유일한 자리입니다.

셋째, 왜 바꿨는지가 기록으로 남습니다. 3개월 뒤의 나는 남이고 AI는 기억이 아예 없습니다. 나중에 «이 기능 왜 이렇게 만들었지?»를 검색하면 그 PR이 나오고, 그걸 AI에게 그대로 읽힐 수 있습니다.

## ③ 본줄기에 보호를 건다

PR을 열기만 하고 이 설정을 안 하면 아무 힘이 없습니다. 언제든 문을 안 거치고 본줄기에 바로 밀어 넣을 수 있기 때문입니다.

| 무엇 | 무슨 뜻 | 왜 |
|---|---|---|
| 브랜치 보호 | 본줄기에 직접 밀어 넣기 금지. 반드시 PR을 거친다 | 문을 세운다 |
| 검사 통과 필수 | 걸어 둔 검사가 초록불이 아니면 합치기 버튼이 안 눌린다 | 문을 지킨다 |
| 관리자에게도 적용 | 저장소 주인인 나도 이 규칙을 지킨다 | 문이 나에게도 문이 된다 |

**셋째를 안 켜면 앞의 둘이 없는 것과 같습니다.** 저장소 주인은 기본적으로 규칙의 예외라, 검사가 빨간불이어도 «관리자 권한으로 병합» 버튼이 뜨고 급할 때 그걸 누르게 됩니다. 막을 사람이 나뿐인데 나를 안 막으면 아무도 안 막는 겁니다.

정말 급하면 규칙을 끄지 않고 되돌립니다(7절). 앞으로 밀어붙이는 것보다 뒤로 물러나는 게 항상 빠릅니다.

## ④ 일부러 어겨 본다

본줄기에 직접 밀어 넣어 보고 **거부 메시지를 눈으로 봐야** 이 절이 끝납니다. 설정 화면의 체크 표시만으로는 문이 잠겼는지 알 수 없습니다.

## ⚡ 따라 하기

1. 가지를 하나 만들고 그 안에서 작업하세요 — 가지 하나가 일 하나입니다. 올리고 나면 GitHub 화면 위에 «Compare & pull request» 단추가 뜹니다.

```bash
git switch -c 기능-로그인화면        # 가지 하나 = 일 하나
# ... AI와 작업 ...
git add -A
git commit -m "로그인 화면 오류 문구를 한국어로 바꿈"
git push -u origin 기능-로그인화면
```

2. 그 단추를 누르거나 터미널에서 PR을 여세요 — 문을 실제로 하나 만드는 것입니다. 열리면 화면에 빨간 줄·초록 줄로 바뀐 부분이 보입니다.

```bash
gh pr create --fill --web
```

3. 저장소에 이 견본을 넣어 두세요 — 매번 PR 본문이 자동으로 채워져서 «왜»를 빠뜨리지 않습니다. 다음 PR부터 본문에 이 다섯 칸이 미리 들어가 있습니다.

```markdown
<!-- .github/pull_request_template.md -->
## ⑤ 무엇을
(한 줄)

## ⑥ 왜
(한 줄 — 3개월 뒤의 나와 AI가 읽습니다)

## ⑦ 어떻게 확인했나
- [ ] 미리보기 주소에서 직접 눌러 봤다
- [ ] 실패하는 경우도 해 봤다(빈칸·잘못된 값)

## ⑧ 되돌리는 법
(이 변경이 사고를 내면 무엇을 되돌리면 되나)
```

4. 저장소 설정에서 본줄기에 보호를 거세요 — 이 절의 핵심입니다. 마지막 항목은 화면 판에 따라 「Include administrators」로 보이기도 하는데 뜻은 같습니다. 주인도 예외 없음.

```
GitHub 저장소 → Settings → Branches → Add branch protection rule

  Branch name pattern:  main

  ☑ Require a pull request before merging
  ☑ Require status checks to pass before merging     ← 다음 절에서 검사를 여기에 넣습니다
  ☑ Do not allow bypassing the above settings        ← 관리자인 나에게도 적용
```

5. 일부러 본줄기에 직접 밀어 보세요 — 문이 잠겼는지는 어겨 봐야 압니다. `protected branch hook declined` 같은 말이 나오면 정상이고, 그러면 방금 만든 커밋을 없애고 가지로 돌아갑니다.

```bash
git switch main
echo "규칙 시험" >> README.md
git add README.md && git commit -m "일부러 본줄기에 직접"
git push
```

```bash
git reset --hard origin/main     # 방금 만든 커밋을 지운다 (밀기 전이라 안전)
```

### 이렇게 해 봤습니다 — 2026-09-09 · 무료로는 문을 «잠글» 수 없습니다

PR을 열고 검사를 걸고 병합까지는 됐습니다. **그런데 브랜치 보호를 켜는 데서 막혔습니다** — *"GitHub Pro로 올리거나, 이 저장소를 공개로 바꾸세요."* 규칙집(ruleset)이라는 다른 방식도 똑같이 거절당했습니다.

무료 계정 + 비공개 저장소 조합에서는 검사 통과를 강제할 수 없습니다. 검사는 돌고 결과도 보이지만 떨어져도 병합 버튼이 살아 있습니다 — 문은 세웠는데 잠금장치가 없는 상태입니다. 길은 셋입니다.

| 길 | 무엇이 되나 | 무엇을 내주나 |
|---|---|---|
| 저장소를 공개로 (추천) | 보호·검사 강제 · 자동 실행 무제한 · 비밀값 스캔 · 코드 검사 전부 무료 | 코드를 남이 봅니다. 비밀값을 코드에 안 두면 문제 없습니다 — 이 커리큘럼이 계속 말하는 그것입니다 |
| 유료로 올리기 | 비공개 그대로 전부 됨 | 돈 |
| 그냥 이대로 | PR 기록·검사 결과는 남음 | 강제가 안 됩니다. 내가 규칙을 지켜야 합니다 |

다음 절의 «자동 실행은 공개는 무제한, 비공개는 시간 제한»도 같은 갈림길입니다. 공개/비공개는 취향이 아니라 무엇이 무료로 되느냐를 가르는 선이고, 배우는 단계라면 공개로 두는 쪽이 훨씬 유리합니다.

## ✅ 확인

- [ ] PR을 한 건 열었고, 화면에 빨간 줄·초록 줄로 바뀐 부분이 보이나
- [ ] 본줄기에 직접 밀어 넣기가 거부되나 — 실제로 해 보고 거부 메시지를 봤나
- [ ] 검사를 통과 못 하면 합쳐지지 않게, 나 자신에게도 적용되게 켰나
- [ ] PR 화면 아래에 미리보기 주소 링크가 붙어 있나

셋째가 «아니오»면 이 절을 안 한 것과 같습니다. 무료·비공개라서 못 켜는 것이면 위의 기록을 보고 길을 고릅니다.

## 📘 말 풀이

**PR(Pull Request, 풀 리퀘스트)** — «이 가지에서 한 변경을 본줄기에 합쳐 주세요»라는 요청서. 요청과 승인 사이에 자동 검사와 리뷰가 들어갑니다.

**병합(merge, 머지)** — 가지에서 한 작업을 본줄기에 합쳐 넣는 것. 합쳐지는 순간이 곧 실서비스로 나가는 순간이라 그 직전에 문을 세웁니다.

**브랜치 보호(branch protection)** — 본줄기에 아무나·아무렇게나 못 들어가게 거는 규칙. «PR을 거쳐라 / 검사를 통과해라 / 주인도 예외 없다» 셋을 여기서 켭니다.

## ⚠️ 함정

**PR만 열고 보호는 안 겁니다.** 가장 흔합니다. 습관만 남고 강제력이 없어서 바쁜 날 그냥 본줄기에 밀어 넣습니다. 관리자 예외를 안 끄는 것도 같은 결과입니다 — 저장소에 나밖에 없는데 나에게만 적용되지 않습니다.

**PR 하나에 열 가지를 담습니다.** 뭐가 문제인지 못 찾고, 되돌리면 멀쩡한 것까지 같이 사라집니다. 한 PR = 한 가지 일.

**제목이 «수정»입니다.** 3개월 뒤에 아무 도움이 안 됩니다. «무엇을 왜»를 한 줄로 씁니다.

**자기 PR을 안 읽고 병합합니다.** 실익 둘째가 통째로 날아갑니다. 열었으면 바뀐 줄은 반드시 눈으로 훑습니다.

**가지를 안 만들고 본줄기에서 작업합니다.** 보호를 걸면 밀어 넣는 순간 거부당합니다. 거부가 정상이고, 그때 가지를 만듭니다.
