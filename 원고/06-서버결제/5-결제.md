## 왜 이걸 하나

이 절이 이 커리큘럼에서 **가장 조심해야 할 자리**입니다.
기술이 어려워서가 아닙니다. **먼저 정해야 할 것을 안 정하고 붙이기부터 하면, 다 만든 뒤에 뜯어야 하기 때문**입니다.

가장 흔한 사고는 이렇습니다.
결제사 한 곳과 계약해서 결제를 다 붙였습니다. 잘 됩니다.
그런데 사용자들이 **카카오페이로 매달 자동결제**를 하고 싶다고 합니다.
확인해 보니 그 길로는 **안 됩니다.** 처음부터 다시 붙여야 합니다.

그래서 이 절은 **붙이는 법이 아니라 고르는 법**부터 시작합니다.
그리고 배우는 단계에서는 **테스트 모드까지만** 갑니다. 실제 계약은 팔 사람이 생겼을 때 합니다.

## 결제대행사와 직계약 — 무엇이 다른가

카드로 돈을 받으려면 카드사와 연결이 돼야 합니다. 개인이 카드사 여덟 곳과 각각 계약할 수는 없습니다.
그래서 사이에서 대신 연결해 주는 회사를 씁니다. **결제대행사(PG)**라고 부릅니다.

여기서 길이 두 갈래로 갈립니다.

| | **직계약** | **통합 결제 서비스** |
|---|---|---|
| 무엇 | 결제 회사 **한 곳**과 내가 직접 계약 | 여러 결제 회사를 **한 번에** 연결해 주는 중개 |
| 붙이는 일 | 그 회사 방식 하나만 익히면 됨 | 한 번 붙이면 결제 수단을 나중에 갈아 끼움 |
| 한계 | **그 회사가 지원하는 수단만** 됩니다 | 각 결제사와의 계약은 여전히 내가 합니다 |
| 예 | 토스페이먼츠 | 포트원 |

**핵심은 마지막 줄입니다.** 직계약은 그 회사가 되는 것만 됩니다.
그게 뭐가 문제냐면 —

## ⚠️ 여기가 가장 중요합니다 — 토스 직계약으로는 카카오페이 정기결제가 안 됩니다

**한 번 더 씁니다. 토스페이먼츠와 직접 계약하는 길로는 카카오페이 정기결제(자동결제)를 붙일 수 없습니다.**

일회성 결제는 됩니다. 매달 자동으로 빠져나가는 정기결제가 안 됩니다.
그리고 **한국에서 구독 서비스를 팔 때 카카오페이 정기결제를 찾는 사용자는 적지 않습니다.**

그래서 결정 순서가 이렇게 됩니다.

```
질문 하나: 카카오페이로 "매달 자동결제"를 받을 생각이 있나?

  예  ──▶  포트원 같은 통합 결제 서비스로 갑니다.
           카카오페이 정기결제(빌링)를 지원합니다.
           일정 규모 아래에서는 이용료가 따로 없다고 안내하고 있습니다
           (금액 기준은 부록 「버전과 값」에).

  아니오 ─▶ 직계약도 괜찮습니다. 토스페이먼츠 쪽이 문서가 친절합니다.
           단, 나중에 마음이 바뀌면 다시 붙여야 합니다.
```

**나중에 바꾸는 비용이 지금 고르는 비용보다 훨씬 큽니다.** 지금 30분 더 씁니다.

## 해외에서도 돈을 받고 싶다면 — Stripe는 길이 아닙니다

해외 결제 이야기가 나오면 거의 모두가 Stripe를 먼저 떠올립니다.
**Stripe는 한국 판매자에게 여전히 닫혀 있습니다.** 계정을 못 엽니다.

해외 결제가 필요하면 **MoR(Merchant of Record)** 방식으로 갑니다.
**Creem**, **Polar** 같은 곳이 한국 판매자를 받는다고 밝히고 있습니다.

MoR은 이름 그대로 **"기록상 파는 사람"**이 그 회사가 되는 방식입니다.
사용자 눈에는 내 서비스에서 사는 것 같지만, 영수증에는 그 회사 이름이 찍힙니다.

| MoR이 대신 해 주는 것 | 대신 |
|---|---|
| 나라마다 다른 세금(부가세 등) 처리 | **떼는 몫이 일반 결제대행사보다 큽니다** |
| 환불·분쟁 응대 | 사용자와 나 사이에 한 겹이 낍니다 |
| 여러 나라 결제 수단 연결 | 정산이 들어오는 주기가 다를 수 있습니다 |

혼자 만드는 사람에게는 **세금 처리를 넘긴다는 것 하나만으로도 값을 합니다.**
다만 국내만 팔 거라면 굳이 갈 필요 없습니다.

## 일회 결제와 정기결제(빌링)는 완전히 다른 일입니다

같은 "결제"라는 말을 쓰지만 만드는 것이 다릅니다.

| | **일회 결제** | **정기결제(빌링)** |
|---|---|---|
| 언제 | 살 때 한 번 | 매달 자동으로 |
| 사용자가 하는 일 | 그때마다 결제 | **처음 한 번만** 카드 등록 |
| 내가 갖는 것 | 결제 결과 | **빌링키** — "이 사람 카드로 청구해도 된다"는 열쇠 |
| 매달 | 없음 | 내 쪽에서 **때가 되면 청구를 걸어야** 합니다 |
| 계약 | 상대적으로 간단 | **따로 심사**를 받는 경우가 많습니다 |

**카드 번호는 절대 내가 저장하지 않습니다.** 저장해서도 안 되고 저장할 필요도 없습니다.
결제사가 준 **빌링키**만 내 표에 넣습니다. 관통 프로젝트의 표를 보면 자리가 이미 있습니다 —
`subscriptions` 표의 `billing_key`, `next_billing`, `status`가 그 자리입니다.

그리고 정기결제는 **매달 저절로 되는 게 아닙니다.** 때가 되면 청구를 거는 일을
내가 돌려야 합니다. 그건 [[08-자율운영/_스테이지|Stage 8]]에서 예약 실행으로 만듭니다.

## 화면에서 성공이라고 뜬 것은 아직 성공이 아닙니다

이걸 모르면 **돈은 안 들어왔는데 서비스는 열어 주는** 사고가 납니다.

결제 결과는 두 경로로 옵니다.

```
① 사용자의 브라우저가 "성공했대요" 하고 돌아온다
      → 화면을 바꾸는 데만 씁니다. 이걸 믿고 서비스를 열면 안 됩니다

② 결제사의 서버가 내 서버에 직접 알려 준다  ← 웹훅(webhook)
      → 이게 진짜입니다. 여기서 확인된 것만 "결제됨"으로 칩니다
```

①은 사용자 손 안에서 벌어지는 일이라 조작될 수 있습니다. ②는 서버끼리 주고받습니다.
**②로 확인된 것만 진짜로 칩니다.**

그리고 ②는 **같은 알림이 두 번 올 수 있습니다.** 결제사가 답을 못 받았다고 생각하면 다시 보냅니다.
그때 두 번 처리하면 구독이 두 개 생기거나 두 번 청구됩니다.
그래서 **받은 알림의 번호를 표에 적어 두고, 이미 있는 번호면 그냥 넘깁니다.**
관통 프로젝트의 `webhook_events` 표가 딱 그 일을 하는 자리입니다. 알림 번호를 열쇠 열로 잡아 두면
같은 번호를 두 번 넣으려 할 때 데이터베이스가 알아서 막아 줍니다.

## 돈이 듭니다 — 미리 알고 가세요

이 절에서 실제 계약까지 가려면 **드는 돈이 있습니다.**

- 결제대행사에 따라 **가입비**가 붙습니다. 한 번 내는 돈입니다.
- **연회비**가 매년 붙는 곳이 있습니다.
- 결제 한 건마다 **수수료**를 뗍니다.
- 여기에 **사업자등록**과 **통신판매업 신고**가 앞에 걸립니다.

구체적인 금액은 본문에 적지 않습니다. 자주 바뀌기 때문입니다 →
[[부록/_스테이지|부록]]의 「버전과 값」에 확인 날짜와 함께 있습니다.

**배우는 단계에서 낼 돈이 아닙니다.** 그래서 —

### 오늘은 테스트 모드까지만 갑니다

결제사들은 **진짜 돈이 오가지 않는 연습용 모드**를 줍니다.
연습용 키를 받아서 붙이면, 정해진 테스트 카드 번호로 결제가 "성공"합니다. 돈은 안 나갑니다.

**테스트 모드로 정확히 어디까지 되는지는 [확인 필요]입니다.**
특히 **정기결제(빌링)를 계약 전에 테스트로 끝까지 돌려 볼 수 있는지**는 결제사마다 다르고,
사업자 심사를 통과해야 열어 주는 곳도 있습니다. 각 결제사의 개발자 문서에서 직접 확인하세요.
확인 안 된 것을 "된다"고 적어 두면 나중에 그 자리에서 멈춥니다.

## 📘 말 풀이

**결제대행사(PG)**
나 대신 카드사·간편결제사와 연결해 주는 회사. 개인이 카드사와 직접 계약할 수 없어서 씁니다.
한 곳과만 계약하는 것이 직계약, 여러 곳을 한 번에 이어 주는 중개가 통합 결제 서비스입니다.

**빌링키(billing key)**
"이 사람 카드로 앞으로 청구해도 된다"는 열쇠. 정기결제는 이걸 받아 두고 매달 청구를 겁니다.
**카드 번호가 아닙니다.** 카드 번호는 내가 저장하지 않습니다.

**웹훅(webhook)**
결제사 서버가 내 서버에 결과를 직접 알려 주는 통로. 브라우저가 가져온 "성공"이 아니라
**이걸로 확인된 것만** 진짜 결제로 칩니다. 같은 알림이 두 번 올 수 있어서 중복을 막아 둬야 합니다.

## ⚠️ 자주 걸리는 함정

- **결제 수단을 안 정하고 붙이기부터 한다** — 이 절의 전부입니다.
  카카오페이 정기결제가 필요한지를 **먼저** 정합니다.
- **브라우저가 가져온 성공을 믿는다** — 웹훅으로 확인하기 전에 서비스를 열어 주면 안 됩니다.
- **같은 웹훅을 두 번 처리한다** — 구독이 둘 생기거나 두 번 청구됩니다. 알림 번호를 저장해 막습니다.
- **결제 비밀키에 `NEXT_PUBLIC_`을 붙인다** — 브라우저에 결제 열쇠를 뿌리는 것입니다. 3절을 다시 보세요.
- **연습용 키와 진짜 키를 섞는다** — 이름이 비슷해서 헷갈립니다. 진짜 키는 실제 계약 전까지 아예 안 만듭니다.
- **금액을 브라우저가 정하게 둔다** — 사용자가 값을 바꿔서 보낼 수 있습니다.
  **금액은 반드시 서버에서 정하고, 결제사에 확인할 때도 서버가 정한 금액과 같은지 대조합니다.**
- **환불·결제 실패를 안 만든다** — 카드 한도 초과나 유효기간 만료로 정기결제는 반드시 실패합니다.
  실패했을 때 무엇을 할지(며칠 뒤 다시 시도, 사용자에게 알림, 그래도 안 되면 정지) 미리 정합니다.
- **테스트 모드에서 다 됐다고 실계약도 될 거라 믿는다** — 심사가 남아 있습니다. 심사에는 시간이 걸립니다.

## ⚡ 이렇게 하세요

### 1. 붙이기 전에 이 표부터 채웁니다 (10분)

종이에 적든 파일에 적든, **답을 적어 두고 시작합니다.**

| 물음 | 내 답 |
|---|---|
| 국내만 파나, 해외도 파나 | |
| 한 번 받나, 매달 받나 | |
| **카카오페이 정기결제가 필요한가** | |
| 그래서 어디로 가나 (직계약 / 포트원 / MoR) | |
| 사업자등록·통신판매업 신고가 돼 있나 | |

세 번째가 **예**면 통합 결제 서비스로 갑니다. 첫 줄이 **해외도**면 MoR을 봅니다.
이 답은 [[02-명세/_스테이지|Stage 2]]에서 배운 대로 결정 기록으로 남겨 둡니다.
3개월 뒤의 나도, AI도 이 결정을 기억하지 못합니다.

### 2. 연습용 키를 받습니다

고른 곳의 개발자 사이트에 가입해서 **테스트(연습용) 키**를 받습니다.
`test_`로 시작하는 이름이 붙어 있는 경우가 많습니다. 3절대로 `.env.local`에 넣습니다.

```
결제_클라이언트_키=test_ck_xxx
결제_비밀키=test_sk_xxx
결제_웹훅_비밀값=whsec_xxx
```

**비밀키와 웹훅 비밀값에는 `NEXT_PUBLIC_`을 붙이지 않습니다.**

### 3. AI에게 붙이게 합니다 — 조건을 먼저 못 박습니다

```
이 프로젝트에 구독 결제를 붙여줘. 아래 조건을 반드시 지켜라.

[결제 방식]
- 결제사: (1번 표에서 고른 곳)
- 지금은 테스트(연습용) 키만 쓴다. 실제 키는 만들지 않는다.

[반드시 지킬 것]
- 결제 금액은 서버에서 정한다. 브라우저가 보낸 금액을 그대로 믿지 않는다.
- 결제사에 최종 확인할 때, 서버가 정한 금액과 같은지 대조하고 다르면 실패 처리한다.
- 브라우저가 가져온 "성공"으로는 구독을 열어 주지 않는다.
  결제사 웹훅을 받았을 때만 subscriptions 상태를 active로 바꾼다.
- 웹훅은 서명을 검증하고, 받은 알림 ID를 webhook_events 표에 넣어 중복 처리를 막는다.
- 결제 관련 키에는 NEXT_PUBLIC_ 접두사를 절대 붙이지 않는다.

먼저 만들 파일과 고칠 파일 목록, 그리고 데이터가 어떤 순서로 흐르는지만 보여줘.
내가 확인하면 그때 실행해.
```

### 4. 테스트 카드로 한 바퀴 돌립니다

결제사 문서에 있는 **테스트 카드 번호**로 결제해 봅니다. 그리고 **표를 직접 열어** 확인합니다.

- `subscriptions`의 상태가 `pending` → `active`로 바뀌었나
- `billing_key`가 들어왔나 (정기결제인 경우)
- `webhook_events`에 알림이 한 줄 들어왔나

**화면이 아니라 표에서 봅니다.** 화면은 거짓말을 할 수 있습니다.

### 5. 일부러 두 번 보내 봅니다

같은 웹훅을 두 번 보내 보고, `subscriptions`에 줄이 **하나만** 있는지 확인합니다.
둘 생기면 중복 막이가 안 걸린 것입니다.

- [ ] **표에서** `subscriptions` 상태가 `active`로 바뀐 것을 봤나 (화면이 아니라)
- [ ] 같은 웹훅을 두 번 보냈을 때 **줄이 하나만** 생기나
- [ ] 결제 비밀키에 `NEXT_PUBLIC_`이 **안 붙어 있나** — 검색해서 확인했나
- [ ] 정기결제가 **실패했을 때 무엇을 할지** 정해서 적어 뒀나
- [ ] 실제 계약에 **얼마가 들고 무엇이 필요한지** 확인해서 적어 뒀나
