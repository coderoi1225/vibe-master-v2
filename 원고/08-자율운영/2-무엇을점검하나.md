## 왜 이걸 하나

점검을 만들 수 있게 되면 **다 만들고 싶어집니다.**
그리고 일주일 뒤에는 알림을 하나도 안 보게 됩니다.

이건 게을러서가 아닙니다. 하루에 알림이 마흔 개 오면 사람은 그걸 **배경 소음으로 처리**합니다.
그러면 정작 진짜 장애가 왔을 때 그것도 같이 못 봅니다.

그래서 이 절은 "무엇을 점검할 수 있나"가 아니라 **"무엇부터 켜고, 무엇은 나중으로 미루나"**입니다.

## 다섯 가지 — 켜는 순서대로

| 순서 | 무엇을 보나 | 왜 이 순서인가 | 어디서 도나 |
|---|---|---|---|
| **1** | **사이트가 살아 있나** | 죽으면 다른 게 다 의미 없다. 만들기도 가장 쉽다 | 깃허브 예약(5분) |
| **2** | **결제 실패** | **돈이 새는 자리.** 사이트는 멀쩡한데 돈만 안 들어오는 상태가 제일 늦게 발견된다 | 결제사 웹훅 + 예약 집계 |
| **3** | **에러가 갑자기 늘었나** | 사용자는 대개 신고하지 않고 그냥 떠난다 | 에러 수집 도구 |
| **4** | **빌드가 깨졌나** | 내가 못 고치는 상태로 굳는 것을 막는다 | Stage 7의 CI가 이미 함 |
| **5** | **인증서 만료 · 링크 깨짐 · 느려짐** | 천천히 오는 것들. 주 1회면 충분하다 | 깃허브 예약(주 1회) |

**오늘 켤 것은 1번 하나입니다.** 1번이 일주일 동안 조용히 잘 돌면 2번을 켭니다.
다섯 개를 같은 날 켜면 어느 것이 시끄러운지 구분할 수 없습니다.

### 1번과 2번의 차이 — "보이는 문제"의 두 얼굴

**사이트가 죽는 것**은 눈에 띕니다. 사용자가 화면을 못 봅니다.
**결제가 실패하는 것**은 눈에 안 띕니다. 화면은 멀쩡하고, 실패한 사람은 조용히 나갑니다.

파는 서비스에서 가장 늦게 발견되는 사고가 이쪽입니다.
그래서 결제는 "실패가 났다"가 아니라 **"평소보다 실패가 많다"**를 봐야 합니다.
어제 1건, 오늘 1건은 정상입니다. 어제 1건, 오늘 12건이면 뭔가 바뀐 겁니다.

### 5번이 왜 5번인가

인증서 만료는 갑자기 오지 않습니다. 남은 날짜가 줄어드는 게 보입니다.
링크 깨짐과 속도 저하도 마찬가지입니다. **매일 볼 필요가 없는 것을 매일 보면 그게 소음이 됩니다.**
주 1회, 정해진 요일 아침에 한 통으로 묶어서 받습니다.

## 📘 말 풀이

**웹훅(webhook)**
"일이 생기면 이 주소로 알려 줘"라고 미리 등록해 두는 것. 내가 물어보러 가는 게 아니라 **저쪽이 먼저 찾아옵니다.** 결제사·깃허브가 이 방식으로 알려 줍니다.

**인증서(SSL certificate)**
주소창의 자물쇠. 기간이 있어서 만료되면 브라우저가 **"위험한 사이트"** 경고를 띄웁니다. 사이트는 멀쩡한데 아무도 못 들어오는 상태가 됩니다.

**에러 수집 도구**
사용자 화면에서 난 오류를 자동으로 모아 주는 서비스. 내가 재현하지 못한 오류도 기록이 남습니다.

## ⚠️ 자주 걸리는 함정

- **⚠️ 무료 감시 서비스 중 개인·비상업 한정인 것이 있습니다.** 대표적으로 이름난 무료 가동 감시 서비스 하나가 무료 요금제를 **개인·비상업 용도로만** 허용합니다. **돈을 받는 서비스를 감시하는 데 쓰면 약관 위반**입니다. 무료 요금제를 고르기 전에 그 서비스의 이용약관에서 "commercial" 이라는 단어를 반드시 찾아보세요. 약관 위반은 어느 날 계정이 잠기는 형태로 돌아옵니다 — 그날은 하필 장애가 난 날입니다.
  - **안전한 대안** — 감시를 남에게 맡기지 않고 **내 저장소의 깃허브 예약 실행으로 직접** 돌립니다. 이건 내 저장소에서 도는 내 코드라 용도 제한이 없습니다.
- **다섯 개를 하루에 다 켜기.** 가장 흔하고 가장 치명적입니다.
- **무료 한도는 대개 에러 수집에서 먼저 걸립니다.** 사이트 감시는 한도가 넉넉한데, 에러는 **한 달에 몇 천 건 단위**에서 끊깁니다 `[확인 필요 — 정확한 값은 부록]`. 오류가 폭주하면 그날 하루로 한 달 치를 다 씁니다.
- **로그인해야 보이는 페이지를 감시 대상으로 걸기.** 로그인 없이 열리는 페이지 하나를 감시용으로 정합니다.
- **점검이 서비스를 느리게 만들기.** 5분마다 무거운 페이지를 열면 그 자체가 부하입니다. 가볍고 고정된 주소 하나를 씁니다.

## ⚡ 이렇게 하세요

**1) 감시 전용 주소를 하나 만듭니다.** 로그인 없이 열리고, 데이터베이스까지 살아 있는지 한 번에 답하는 자리입니다.

```
/api/health  →  {"ok": true}
```

AI에게 시킬 때는 이렇게 씁니다.

```
/api/health 라는 주소를 하나 만들어줘.
- 로그인 없이 열려야 한다
- 데이터베이스에 아주 가벼운 쿼리를 한 번 던져 보고,
  성공하면 {"ok": true} 를 200으로,
  실패하면 {"ok": false, "reason": "..."} 를 503으로 돌려준다
- 개인정보나 내부 설정값은 절대 담지 않는다
```

**2) 점검 다섯 개를 표로 적어 저장소에 둡니다.** 파일 이름은 `점검표.md`.

```markdown
| 무엇 | 주기 | 어디서 | 켠 날 | 지난달 울린 횟수 |
|---|---|---|---|---|
| 사이트 살아있나 | 5분 | 깃허브 예약 | 2026-09-09 | |
| 결제 실패 급증 | 1시간 | 깃허브 예약 | (아직) | |
| 에러 급증 | 실시간 | 에러 수집 도구 | (아직) | |
| 빌드 깨짐 | PR마다 | Stage 7의 CI | | |
| 인증서·링크·속도 | 주 1회 | 깃허브 예약 | (아직) | |
```

**"지난달 울린 횟수" 칸이 이 표의 핵심입니다.** 다음 절의 「한 달 무시한 알림은 지운다」가 이 숫자로 판정됩니다.

**3) 오늘은 1번만 켭니다.** 앞 절에서 만든 `살아있나.yml`이 그것입니다. 2번은 다음 주에.
