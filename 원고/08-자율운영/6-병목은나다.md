## 왜 이걸 하나

앞의 다섯 절은 **기계가 나를 부르는 법**이었습니다.
이 절은 반대입니다. **내가 기계 여럿을 보는 법**입니다.

이 장에서 만든 것들이 늘어나면 어느 순간 이렇게 됩니다 —
야간 점검이 돌고, 긴 작업 하나가 멀티플렉서에서 돌고, 다른 창에서 뭔가 만들고 있습니다.
셋이 넷이 되고 넷이 여섯이 됩니다. 그리고 이런 일이 생깁니다.

> **막힌 에이전트가 20분, 30분씩 나를 기다리고 있는데 나는 그 상황을 모르고 있었습니다.**

메타에서 일하는 한 개발자가 동시에 열한 개를 돌리며 겪은 일입니다. 그가 남긴 문장이 이 커리큘럼 전체를 관통합니다.

> **"에이전트를 많이 돌릴수록 병목은 결국 나라는 게 뼈저리게 느껴지더라고요."**

## 왜 병목이 나인가

일을 시키는 속도는 빨라졌습니다. 한 문장이면 됩니다.
**결과를 보는 속도는 그대로입니다.** 눈은 하나고, 창은 여섯입니다.

그래서 이런 모양이 됩니다.

```
에이전트 1  ████████ 돌아가는 중
에이전트 2  ████ 끝남 (내가 20분째 모름)
에이전트 3  ██ 막힘 — 승인을 기다리는 중 (30분째)
에이전트 4  ████████ 돌아가는 중
```

**3번이 문제입니다.** 3번은 일하고 있지 않습니다. 나를 기다리고 있습니다.
그런데 화면만 봐서는 1번과 3번이 똑같이 생겼습니다. 둘 다 글자가 떠 있는 창입니다.

**터미널은 "지금 승인을 기다리는 중"과 "지금 열심히 도는 중"을 구분해 주지 않습니다.**
그냥 글자를 보여 줄 뿐입니다. 그래서 내가 탭을 하나씩 돌면서 확인해야 하고, **그 순간 내가 병목이 됩니다.**

## 상태를 색으로 본다

해결의 핵심은 도구가 아니라 **한 가지 발상**입니다.

> **글자를 읽지 말고, 상태를 색으로 보라.**

네 가지면 충분합니다.

| 색 | 상태 | 내가 할 일 |
|---|---|---|
| 🔵 | **돌아가는 중** | 없음. 건드리지 않는다 |
| 🟢 | **완료 · 안 읽음** | 시간 날 때 읽는다 |
| ⚪ | **읽음** | 없음 |
| 🔴 | **막힘 — 내 승인 대기** | **지금 여기로 간다** |

**빨간 것만 보면 됩니다.** 나머지 셋은 볼 필요가 없습니다.
여섯 개를 돌려도 내가 봐야 하는 건 대개 하나거나 없습니다.

이걸 갖추면 여섯 개를 돌리는 게 하나를 돌리는 것보다 덜 피곤해집니다. **여섯 개를 다 보는 대신 하나만 보기 때문**입니다.

## 백그라운드와 화면의 차이

일을 맡기는 방식은 둘입니다. **이 둘의 차이를 아는 것이 이 절의 실전입니다.**

| | 백그라운드로 보내기 | 화면으로 띄우기 |
|---|---|---|
| 보는 것 | **결과만** | **진행 과정** |
| 중간에 끼어들기 | 못 한다 | **된다** |
| 언제 | 결과가 뻔한 일 · 조사 · 정리 | 처음 하는 일 · 틀리면 되돌리기 힘든 일 |
| 피로 | 낮다 | 높다 |

**화면으로 띄우면 가로챌 수 있습니다.**
30분짜리 작업이 5분째에 엉뚱한 방향으로 가는 게 보이면, 거기서 **"이건 이렇게 하면 안 돼"**라고 끊을 수 있습니다.
백그라운드로 보냈으면 30분 뒤에 30분치 잘못된 결과를 받습니다.

**판단 기준 한 줄** — **되돌리기 쉬우면 백그라운드, 되돌리기 어려우면 화면.**

## 자기 전에 돌려놓고 잔다

이 절이 실제 리듬으로 바뀌는 자리입니다.

```
밤   — 긴 작업 두세 개를 멀티플렉서 안에서 시작하고 잔다
아침 — 일어나서 빨간 것만 확인한다. PR 몇 개가 만들어져 있다
출근 전 — 또 몇 개 돌려놓고 나간다
이동 중 — 팟캐스트를 듣는다
도착  — 끝나 있다
```

**시간을 쓰는 게 아니라 시간을 겹치는 것**입니다.
내가 자는 8시간과 이동하는 1시간은 원래 아무것도 안 하던 시간입니다.

여기에 앞 절의 울타리가 붙어야 합니다. **밤에 도는 것은 PR까지만** — 그래야 아침에 읽고 고를 수 있습니다.

## 사람의 역할이 옮겨간 자리

이 리듬에 익숙해지면 하루의 모양이 바뀝니다.

**만드는 시간은 줄고, 검증하는 시간이 늘어납니다.**
그리고 그게 잘못된 게 아닙니다. 만드는 건 여럿이 동시에 할 수 있고, **판단은 나만 할 수 있기 때문**입니다.

그래서 이 커리큘럼의 세 조각이 한 문장으로 모입니다.

- 1인 회사의 병목은 **만드는 쪽이 아니라 보는 쪽**이다
- 1인이 자동화에 실패하는 이유는 **검수할 사람이 없어서**다
- 사람의 역할은 **검증**이다

## 📘 말 풀이

**막힘(blocked)**
에이전트가 일을 멈추고 사람의 대답을 기다리는 상태. "이 명령 실행할까요?" 같은 물음이 뜬 채 멈춰 있습니다. **일하는 중이 아니라 놀고 있는 상태**라 가장 먼저 찾아야 합니다.

**백그라운드(background)**
눈앞에 띄우지 않고 뒤에서 돌리는 것. 결과가 끝나야 돌아옵니다.

**브리프 파일(brief)**
여러 에이전트에게 일을 나눠 줄 때, 각자에게 "너는 이걸 해라"를 적어 건네는 짧은 파일. 말로 설명하는 대신 파일로 넘기면 **내가 같은 말을 여러 번 하지 않아도 됩니다.**

## ⚠️ 자주 걸리는 함정

- **개수를 자랑하기.** 동시에 몇 개를 돌리느냐는 성과가 아닙니다. **막힌 것을 몇 분 안에 발견하느냐**가 성과입니다.
- **셋을 넘겨서 시작하기.** 상태를 볼 방법을 갖추기 전에는 **둘까지**입니다. 셋부터는 반드시 놓칩니다.
- **다 백그라운드로 보내기.** 편하지만 가로챌 기회를 통째로 버립니다. 처음 하는 일은 화면으로.
- **같은 폴더를 두 에이전트가 동시에 고치게 하기.** 서로 덮어씁니다. 겹치는 파일을 만지는 일은 **순서대로** 시킵니다.
- **밤에 돌리는 것에 승인이 필요한 일을 섞기.** 아침에 가 보면 8시간 동안 막혀 있습니다. 밤 작업은 **끝까지 혼자 갈 수 있는 것**만 고릅니다.

## ⚡ 이렇게 하세요

**1) 방 이름을 붙이는 규칙을 정합니다.** 이름이 곧 상태 표시입니다.

```bash
tmux new -s 점검-야간
tmux new -s 작업-로그인화면
tmux new -s 조사-경쟁사
```

**2) 한눈에 보는 명령을 하나 만들어 둡니다.**

```bash
# 살아 있는 방과 마지막으로 붙었던 시각
tmux ls -F '#{session_name}  마지막확인:#{t:session_last_attached}'
```

**3) 막힌 것을 찾는 법 — 화면 글자를 긁어서 봅니다.**

```bash
# 각 방의 마지막 줄만 뽑아 본다. 물음표나 (y/n) 이 보이면 그게 막힌 것이다
for s in $(tmux ls -F '#{session_name}'); do
  echo "── $s"
  tmux capture-pane -p -t "$s" | tail -3
done
```

**4) 밤 작업을 시킬 때 이 문장을 앞에 붙입니다.** 막힘을 미리 없애는 프롬프트입니다.

```
이 작업은 내가 자는 동안 혼자 돈다. 나는 중간에 대답할 수 없다.

- 중간에 나에게 물어보지 마라. 물어보고 싶은 지점이 생기면
  거기서 멈추지 말고, 가장 안전한 선택을 하고 그 사실을 기록해라.
- 판단이 갈리는 지점은 모두 "확인이 필요한 것" 목록에 모아서 마지막에 보여 줘라.
- 되돌리기 어려운 일(파일 삭제, 배포, 데이터 변경)은 하지 마라.
  필요하다고 판단되면 하지 말고 목록에만 적어라.
- 결과는 PR 하나로 만들고, 본문 맨 위에 "확인이 필요한 것"을 적어라.
```

**5) 아침에 하는 것은 하나입니다.** 방 목록을 열고 **막힌 것부터** 봅니다. 완료된 것은 그다음입니다.
