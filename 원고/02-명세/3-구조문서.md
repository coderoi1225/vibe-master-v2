요구사항 문서는 «무엇을» 만들지를 적은 것입니다. 구조 문서는 그게 어디에 놓이고 어떻게 이어지는지를 적은 것입니다.

## ① 네모와 화살표만 남긴다

이게 없으면 AI가 같은 일을 하는 코드를 여러 군데에 만듭니다. 회원 정보를 저장하는 곳이 두 군데, 이메일을 보내는 코드가 세 군데 생깁니다. 그러면 하나를 고쳐도 다른 하나는 남아서 «고쳤는데 안 고쳐졌다»가 됩니다.

기술 문서라고 하면 겁이 나지만, 실제로 필요한 건 **네모와 화살표**뿐입니다.

- 네모 = 무언가가 놓여 있는 자리 (화면 하나, 저장소 하나, 바깥 서비스 하나)
- 화살표 = 무엇이 어디로 가는가 (사람이 누른다, 정보가 저장된다, 메일이 나간다)

그림 도구는 필요 없습니다. AI는 그림을 못 읽지만 글은 정확히 읽으니, 글로 쓰는 편이 오히려 낫습니다.

## ② 네모 세 종류를 가른다

| 종류 | 무엇 | 예 |
|---|---|---|
| 보이는 것 | 사람이 눈으로 보고 누르는 화면 | 가입 화면 · 마이페이지 · 결제 화면 |
| 쌓이는 것 | 사라지면 안 되는 정보가 남는 곳 | 회원 명단 · 구독 상태 · 보낸 기록 |
| 빌려 쓰는 것 | 내가 안 만들고 남의 것을 쓰는 자리 | 이메일 보내는 서비스 · 결제 · 글 요약 |

**세 번째가 중요합니다.** 내가 안 만드는 것을 적어 두지 않으면 AI가 그걸 직접 만들려고 듭니다. 결제를 직접 만들면 안 되고 빌려 씁니다.

## ③ 한 장짜리 예를 읽는다

「하루 5분 뉴스 요약을 이메일로 보내는 구독 서비스」의 구조 문서 본문입니다.

화면 — 사람이 보는 것 넷

| 화면 | 여기서 하는 일 |
|---|---|
| 첫 화면 | 뭘 해 주는 서비스인지 보고, 가입 버튼을 누른다 |
| 가입 화면 | 이메일을 넣고 관심 분야를 하나 고른다 |
| 마이페이지 | 분야를 바꾸거나, 결제를 해지한다 |
| 결제 화면 | 카드 정보를 넣는다 — 우리가 만들지 않는다. 빌려 온 화면을 띄운다 |

쌓이는 것 — 표 셋

| 표 | 무엇이 한 줄씩 쌓이나 |
|---|---|
| 회원 | 이메일 · 고른 분야 · 가입한 날 |
| 구독 | 누가 · 언제부터 · 지금 살아 있나 죽었나 |
| 발송 기록 | 언제 · 누구에게 · 성공했나 실패했나 |

빌려 쓰는 것 — 넷

| 무엇 | 어디에 쓰나 | 못 쓰게 되면 |
|---|---|---|
| 회원 저장소 | 위의 표 셋을 담는 곳 | 서비스 전체가 멈춘다 |
| 이메일 발송 | 아침에 메일을 실제로 쏘는 곳 | 메일이 안 나간다 |
| 결제 | 매달 돈을 받는 곳 | 새 가입만 막히고 기존은 돈다 |
| 글 요약 | 기사를 다섯 줄로 줄이는 곳 | 요약이 빈 채로 나간다 |

하루의 흐름 — 화살표 한 줄

```
사람이 가입 → 회원 표에 한 줄 추가 → 결제가 되면 구독 표에 살아 있음 표시
매일 아침 정해진 시간 → 살아 있는 구독자를 훑는다 → 기사를 모은다
→ 글 요약에 맡긴다 → 이메일 발송에 넘긴다 → 발송 기록에 한 줄 남긴다
```

이게 전부입니다. **A4 한 장을 넘기지 않습니다.** 넘어간다면 안 만들 것을 너무 많이 넣은 것이니 [[02-명세/2-요구사항|2절]]의 「안 만들 것」으로 돌아갑니다.

## ④ 못 쓰게 되면 칸을 채운다

빌려 쓰는 것은 언젠가 멈춥니다. 값이 오르거나, 문을 닫거나, 우리 나라에서 못 쓰게 됩니다. 그때 **무엇이 같이 멈추는지**를 지금 한 줄로 적어 두면, 갈아탈 때 무엇을 손대야 할지 바로 압니다.

이 칸이 뒤 Stage에서 그대로 쓰입니다 — 서버·결제를 붙일 때, 그리고 문제가 났을 때 원인을 좁힐 때.

## ⚡ 따라 하기

1. `docs/ARCHITECTURE.md` 파일을 만드세요. 요구사항 문서 옆에 나란히 두려는 것입니다. `docs` 폴더에 파일 둘이 보이면 됩니다.
2. `PRD.md`를 첨부하고 아래를 붙여넣으세요. 그림 대신 글로 쓰게 하는 것입니다. 네 칸짜리 문서가 표와 화살표 한 줄로 돌아와야 합니다.

```
첨부한 PRD.md를 읽어라. 코드는 짜지 마라. 문서 하나만 만들어라.

이 서비스의 구조를 ARCHITECTURE.md로 정리해라.
그림·다이어그램을 쓰지 말고 전부 글과 표로 써라.
비개발자가 읽을 것이니 전문 용어를 쓰면 괄호 안에 쉬운 말로 풀어라.

구조는 네 칸으로 고정한다.
1. 화면 — 사람이 보는 화면 목록과 각 화면에서 하는 일
2. 쌓이는 것 — 사라지면 안 되는 정보를 표로. 각 표에 무엇이 한 줄씩 쌓이는지
3. 빌려 쓰는 것 — 우리가 직접 만들지 않고 남의 서비스를 쓰는 자리.
   각각 "못 쓰게 되면 무엇이 같이 멈추는가"를 한 줄로
4. 하루의 흐름 — 사람이 가입해서 메일을 받기까지를 화살표 한 줄로

전체를 A4 한 장 안에 넣어라. 넘치면 무엇을 뺄지 나에게 물어라.
아직 정해지지 않은 것은 지어내지 말고 [아직 안 정함]이라고 써라.
```

3. 돌아온 글을 **소리 내어 읽으세요.** 못 읽는 단어가 나오면 그 자리에서 되물으세요 — 내가 못 읽는 지도는 나중에 내가 못 씁니다. 두 줄 설명과 비유 하나가 돌아옵니다.

```
방금 문서에서 내가 모르는 말이 있다. "○○"가 무엇인지
12살에게 설명하듯 두 줄로 알려줘. 비유를 하나 붙여줘.
```

4. `[아직 안 정함]`이 몇 개인지 세세요. 그게 지금 내가 안 정한 것의 개수입니다. 그중 하나를 오늘 정해서 문서의 그 자리에 적으세요.

## 📘 말 풀이

**아키텍처(architecture, 구조)** — 건물로 치면 «어느 방이 어디에 있고 복도가 어떻게 이어지나». 코드로 치면 화면·저장소·바깥 서비스가 어떻게 연결돼 있나입니다.

**데이터베이스(database, 저장소)** — 사라지면 안 되는 정보를 줄 단위로 쌓아 두는 곳. 엑셀 표를 아주 많이, 아주 빠르게 다루는 것이라고 보면 크게 틀리지 않습니다.

## ⚠️ 함정

**그림 도구부터 찾습니다.** 예쁘게 그리는 데 두 시간을 씁니다. AI는 그림을 못 읽으니 글로 씁니다.

**어려운 말로 쓰려고 합니다.** «인증 레이어» «비동기 큐»를 흉내 내면 나중에 내가 못 읽습니다. 내가 아는 말로 쓰고, 어려운 이름은 AI가 코드에서 알아서 붙입니다.

**빌려 쓰는 것을 안 적습니다.** 안 적으면 AI가 직접 만들려 듭니다. 특히 결제와 로그인은 절대 직접 만들지 않습니다.

**문서와 실제가 어긋난 채로 둡니다.** 만들다가 구조가 바뀌면 그 자리에서 이 문서를 고칩니다. 어긋난 지도는 없는 지도보다 나쁩니다.
